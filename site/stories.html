A catalog, and an order to build it

The R640 was waiting on a cable. There was nothing to flash, so the afternoon went into a question the lab had been answering piecemeal for a month: what does a person expect from a hypervisor they can leave alone, and which of those things have we actually seen on this machine?

b91f1292 wrote it down as one catalog. Letters A through K, 129 rows. Twenty-six had lived. Four were in flight. Ninety-nine were only named. Shipment 1, the dedicated box, is 67 of them. The count is a table of contents. It is not a score. HDA stayed 99%.

A catalog is how a buyer reads. It is a bad way to decide what to pick up on a Tuesday, because the dependencies cross the letters and the rack is one machine. e94b47ea gave the work an order: waves 0 through 17, and a verification wave that runs beside them. Each wave has one iron thread. Everything else in the wave can be done while that thread waits. The tool prints the current wave. That afternoon it printed wave 1, Close M8.9, iron thread D3 — the port with no cable. 250dc961 put the same instruction where the next session would see it: on “what next”, run ./tools/sync-sku-site.sh --next and answer from the printout.

The same day had a second fact, older than the catalog. Main had fallen 238 commits behind a chain of stacked branches, from ac3b92cd to 250dc961, because each new branch had started on the previous one. 7b34cf18 split the public record into three pages with three jobs: HDA is how we got here, the SKU page is what you get and what is being built, LOI is whether we are ready to talk. 155c49c7 wrote the rule that was supposed to make the lag impossible to repeat. Branch off main. Merge when the gate closes. Never chain. It also recorded that 165 of those chained pull requests were closed.

Nothing in the catalog changed status because a story was written about it. Everest stayed closed. The rollback for that loop stayed v0.1.0-everest-closed.

Fifteen frames, and the cable was not there

This one is open. The close we wrote down wants a frame from the guest’s own MAC to leave :39, and a login to that address from another machine. Neither has been seen.

A form that remembered

Create still made a disk with no network card. a5bf8d4e kept a NIC record for the spare on the host, and did not write the sector. fcdec904 put the form on the page: mode, address, Save. Save it, refresh the guest list, and the MAC came back. d2ee5015 could fill the same blanks from a DHCP offer and then stop, on purpose, before Save. 19ada6c9 aimed that discover at the other LOM port, function 1, 01:00.1, the address that ends in :39, and refused to send it out the port the SPA already owned. The APE lock stayed with iDRAC. On that commit the rings were not programmed yet, and an offer still did not Save.

The queue that could not wake itself

Then the guest did send something, and the console went quiet. For a week the connect sat in poll_idle. 0dcc1cea finally printed the minutes after the first frame. One IRQ 11 and one timer tick got in (take11=1 take0=1 inj=2). After that the inject path had nothing it was willing to deliver (skip_idle=385). The slave interrupt controller sat with 0x08 in service and the virtio-net line unread. Linux sent a specific end-of-interrupt, 0x60, and the master went from 0x05 to 0x01: the wrong bit cleared, the timer left in service, no more ticks.

c9f4451a fixed that handshake. The chain looked healthy — idtv=1 reinj=1 eoi_s=21 take0=149, the clock keeping up with the PIT — and then, every five seconds, the kernel gave up on its own transmit queue: 

NETDEV WATCHDOG: transmit queue 0 timed out

Linux stops a virtio transmit queue when fewer than 19 descriptors are free, and it only wakes the queue again at 19. An eight-entry ring never has 19 free. The watchdog was the queue noticing that it could not be woken. 11cd3ed9 made the rings 256 deep, the size QEMU had been using all along.

The page that already knew

d7e2e24f brought the guest up clean. No watchdog. COM2 counted TX 15 RX 0. The guest asked for 10.99.99.1 and the answer was FAILED. The connect ended exit:124.

iDRAC had been showing the reason for the whole experiment. Integrated NIC port 4, B0:26:28:5C:5A:39, Link Down, auto-negotiation Disabled. Port 3, the SPA, Up at 1000 Mbps. We had armed a MAC, set a port mode, and counted fifteen frames on a PHY that had nothing plugged into it.

The story stops on that screen. D3, D7, and D8 stay in flight. HDA stays 99%. Everest stays closed.

Ubuntu, from the library, to a prompt

On 4 October we wrote the bar down and admitted we were not at it. ADR-020 (18d136c2) calls the machine RayNu VM Generation 1: one specified guest that boots an operating system the way the vendor shipped it. Phases 0 through 5. What had lived was a patched Alpine, reboot to its own disk, with the patcher and the auto-answer still on the product path.

The Ubuntu file was already on the spare. 93088c32 had stored ubuntu-26.04-live-server-amd64.iso. The page sat at ISO 100%. COM2 had said library CD stored. The next boot, 27d4e540, attached that file as vdb and then booted the Cruzer Alpine anyway (cd_bytes=1042284544). The disc we had spent the upload on was not the disc the firmware opened. After that, the file waits until Guests chooses the ISO row.

Three ways to refuse a shim

Ubuntu’s own BOOTX64.EFI is a shim, and it wanted things Alpine had never asked for.

5cb54836 ran for 180 seconds, read zero blocks, and spent the time in AllocatePool of type 0. We had been declining that pool type. The next EFI serves it as loader data.

0aa0a78d got further and stopped on MokListRT. SetVariable was unsupported. Secure Boot’s runtime list is how a shim remembers what it has been told to trust. We kept a variable store for the length of the boot and minted a null protocol handle.

8822dbfa reached the open of grubx64.efi and came back Not Found, blk_rd=0. The path we had published was the CD-ROM device itself. Shim turned that into a directory prefix and looked for GRUB in the root of the FAT. On this disc grubx64.efi sits beside \EFI\BOOT\BOOTX64.EFI. The next EFI publishes that file node, and opens a relative name against the directory handle.

A menu, a silent kernel

The menu did appear. On 90f64bcf GNU GRUB 2.14 was counting down, at 22 seconds, when our wall cap fired at wall_ms=180007 with only 17 block reads behind it. We gave the next boot ten minutes. 9147cad0 used them up and died at GRUB’s own 1s, wall_ms=600005. A second on that menu was about twenty seconds of the rack. That clock has its own story.

When the menu could finish, the kernel left without saying goodbye. 87979e32 reached ExitBootServices and virtio DRIVER_OK, and COM2 never printed Linux version. The line in the stock grub.cfg has no serial console. We append console=ttyS0 for the library CD, at StartImage, and we do not write it back into the stored file.

That was not enough. GRUB 2.14 does not hand the kernel to StartImage. It jumps. 6865b5ab and 4e9ebcdb both reached the same silence, and the block reads told us the menu file was coming through BlockIo, out of the ISO9660 directory, where our LoadOptions never went. So the read view of that linux line grew console=ttyS0, and the bytes on the spare stayed the bytes the operator uploaded.

A CPU that introduced itself wrong

a71fbb3d finally printed Linux version 7.0.0-14-generic, and then the initrd unpack failed with a write error. We had told the guest it had 256 MiB. About two gigabytes were already mapped behind it. 6a7e72b1 gave it the tail (bytes=2113929216 tail=1845493760), unpacked the initrd, and died in /init on a sentence we had not seen from Alpine: 

CPU ISA level is lower than required

glibc wanted AVX, and our CPUID had not told it the OS would save that state. The next EFI publishes XCR0. 8c6bfa85 lived XCR0 at 0x2ff and libc refused again. This time the vendor string was GenuineIntEl. We had been masking the X2APIC bit on every leaf, and leaf 0 is where the twelve-character vendor lives. Flip one character and userspace never bothers to read leaf 1. The mask moved to leaf 1 only.

1b01c2d8 got a vendor glibc would believe. udev started. Then a filesystem notification waited forever in synchronize_srcu. Linux 7 starts that grace period with a self-IPI, and we had been throwing local-APIC writes away. 6d630acc delivered self-ipi vec=0xf6 four times. Casper mounted. The getty came up. 

Welcome to Ubuntu 26.04 LTS!

The tty was waiting for cloud-init. There is no guest NIC on this boot, and cloud-init was waiting for a network that was never going to answer. 9df8d68a put cloud-init=disabled on the kernel line. The wait stayed. 5f24b74e reached cloud-init’s own “final” and still did not draw the language list. The next EFI adds ci.ds=None and masks the casper checksum and the snap seed.

Fourteen hours of one sector

674f74c8 drew the language list. Curtin started extracting onto vda. Then the familiar line: Stage 46 hold, at the sixteen-million-exit cap, in the middle of a copy. 806d8961 raised the cap to 256 million. The language list came back. Installing system started. The log did not move for about fourteen hours, and there was no hold this time. The guest was working. Every sector was its own trip through the PERC mailbox.

c4a3ef1b posts 64 KiB when the spare allows it, 4 KiB when it does not, one sector when it must. The copy finished. The kernel was on the disk. GRUB’s install then failed, and dmesg had the reason: Unable to switch EFI into virtual mode (status=8000000000000003). That status is SetVirtualAddressMap unsupported — the same runtime call we had been papering over with efi=noruntime on Alpine, which cannot be injected into this ISO. 996492fc accepts the call and rewrites the runtime pointers. Subiquity reached Installation complete.

The disk that could not find its own GRUB

Start on the new row booted the wrong Alpine. The Ubuntu disk was the next GPT, ten gibibytes at the 18 GiB mark. When 1c278f67 started that row, it opened the removable shim and the shim said Failed to open grubx64.efi. The GRUB Ubuntu had installed was \EFI\ubuntu\grubx64.efi, not the one beside BOOTX64.EFI.

252c04cd opened grubx64.efi and stopped at grub>. Shim had found the file. Our buffer load had then cleared LoadedImage.FilePath, so GRUB woke up with no prefix and never opened its own grub.cfg. 9abd4870 staged the shim again, opened GRUB again, and stopped at the same prompt with no FilePath line at all. The next EFI skips the shim when grubx64.efi is already there and launches that file with the path already published.

89a67dc4 did exactly that, printed the stub search.fs_uuid 6ded2137-de53-4881-93df-8bbdeb2b20ec, and stopped at grub> once more. The device handle was the whole disk. GRUB went looking for its files at LBA 0. The ESP is partition 1, at LBA 2048. The next EFI gives the loader that partition’s handle, so GRUB can call the disk hd0,gpt1.

An initrd that knew its own length

1149d279 drew the menu. *Ubuntu. Then the stub, every time, with the same status: 

Failed to load initrd: 0x8000000000000001

The ESP handle was alive (part=1 lba=2048). The failure moved one function call at a time, and the number never changed. GRUB’s LoadFile2 returns not-found unless the path remainder is an End node, and the stub treats any other answer to its size query as a load error. 4f65682f got matched=20 remainder=End and the same error, because this was not the LoadFile2 struct GRUB had registered. fa3ccb64 entered that struct (buf=0x0, then buf=0x415f000) and the copy came back buffer-too-small, which the stub reports as the same load error. 826ca6e9 printed sz=34338680 — the length was real, there was no blk fail — and still returned the error. The next EFI reads that ext4 file into the stub’s buffer and returns success from the shim.

The prompt

c3a70e62, build: sha=c3a70e623aec, choice 4. The library file was still waiting. Clear ISO had not been clicked. The ISO-INSTALL-OK in this log is the firmware handing off, the same words as an install, a different event.

vikkp@raynusrv2:~$

Then, on the same COM2, after the prompt:

The wipe is one sector, the ISO signature. UBUNTU0, the 8 GiB window, and the Ubuntu disk stay. vda is 10 GiB, vda1 vda2 vda3. The 2.9 TB virtual disk is still hidden behind that tail.

The login is real, and the bar from 4 October is still ahead of it. The stored ISO was the vendor’s file. The boot that reached the prompt had appended console=ttyS0 on the way, and the Alpine answerer is still in the tree for the other disc. Unmodified media stayed at 25 on the login row. A GRUB second, on a wall clock

GRUB counts down in its own seconds. Twice, a fortnight apart, we watched that countdown and a wristwatch disagree, and both times the prompt at the end was grub>.

The only sector we were willing to mention

c4a41a17 found the installed Alpine and stopped at the prompt. We had taught that EFI to speak up once, the first time a read went past the GPT pin, and then to be quiet. The one line it printed was ours: the firmware, staging BOOTX64.EFI, reading the FAT boot sector. GRUB’s own reads came after, with no serial left to name them. 

boot: Stage 46 disk past pin lba=2048 n=512 ok (not ISO-INSTALL-OK)
boot: RayNu-F found \EFI\BOOT\BOOTX64.EFI bytes=139264 (F7 disk; not ISO-INSTALL-OK)
image=DISK-BOOTX64

No wall-cap line. The operator powered the machine off at the prompt.

Boot 2 of the soak EFI, e5cca2e0, with usbsoak.txt taken off the stick, staged the same file and stopped in the same place. This time the cap spoke. 

RayNu-F stop wall-cap exits=301551616 wall_ms=180005 svc=301551566 svc_err=1 conout_ok=1 blk_rd=33 blk_wr=0 allocs=6 free_pages=62553
Stage 46 product ISO hold

Three minutes of wall time. Thirty-three block reads. blk_rd=33 is the same count as d60431ee, the boot where a RAM pin had been serving LBA 0 through 33 and GRUB had never been allowed a sector past it. The function we had named “past pin” went back and read LBA 0 again, inside GRUB’s first read outside the pin. Nothing was written. The Toshiba was the same disk we had started with. Nobody got a login.

Twenty wall seconds to a GRUB second

The Ubuntu menu met the cap from the other direction. 90f64bcf drew GNU GRUB 2.14. The countdown said 22 seconds. The wall said wall_ms=180007, and only 17 blocks had been read. We raised the cap to ten minutes so a 30 second menu, and the kernel read after it, could finish.

9147cad0 spent the ten minutes and died with GRUB still showing 1s. wall_ms=600005. blk_rd=17. A second, to GRUB, had been about twenty seconds of the room. PIT channel 2 is how that firmware calibrates a delay, and channel 2 had not been waiting. The next EFI waits a real 55 milliseconds on that counter. Neither of these boots reached the kernel. The menu is a clock, and the clock was the bug.

HTTPS, before the guest

We already had a TLS stack. On the host, 77e3e33c put a plaintext listen in front of the management socket and bc640594 fed it through rustls until the SPA came back over TCP. The minute before RayNu-F

928d6224, build: sha=928d62241967. The PRE-EBS window was still plaintext SNP at http://10.99.99.140:8443/, and it timed out. The operator did not curl it. The iron chase that closed every door except the one that mattered

ADR-016 is the adult decision. ADR-014 builds that on a private VMCS — the guest gets its own firmware, its own EPT, its own VMCS, separate from the E4 SHELL path.

The firmware's first act: kill the hypervisor

Stage 37 VMLAUNCHed the retained ESP OVMF.fd on the private VMCS (RAYNU-V-M7-E5-OVMF-VMLAUNCH-OK). Stage 38 found the first wall: OVMF's SEC phase runs mov cr4, 0x640 — which clears VMXE. On a guest that shares CR4 with the host, that is an instant #GP → triple-fault. The fix is the same lesson E4 Linux taught: the host owns CR4.VMXE. With 32 MiB of low RAM and a short resume, OVMF stayed alive past the first triple-fault (RAYNU-V-M7-E5-OVMF-ALIVE-OK).

Stage 39 walked OVMF out of the SEC tail — PEI PCI config, firmware COM, HLT, COM1/COM2 forwarded (RAYNU-V-M7-E5-OVMF-PAST-SEC-OK). Stage 41 put i440FX and IDE where PEI's Device-ID probe actually looks (00:00.0, DID 0x7010) for the DXE platform boot attempt (RAYNU-V-M7-E5-OVMF-DXE-OK). 2026-08-19 · Dell PowerEdge R640 · BCM5720 · APE NCSI

Don’t take the APE PHY

The day before E3b closed, almost every native-NIC EFI printed the same two letters: bmsr=7949 — link down — then skipped listen. COM2 looked busy. The jack had no carrier.

Broadcom’s APE firmware talks NCSI to iDRAC over the same copper the host wants. A Linux-style BMCR_RESET, a PHY lock, or a reset that drops APE’s phylock, and you steal the analog from the BMC. Dedicated iDRAC stays up. Host LOM goes dark. SOL console com2 is not a substitute for a link on :38.

Several Cruzer prefixes are retired for that reason (42b42c99, ec08c00f, 1404f055, skip-CORECLK 26573eb1, and any take-PHY with ape-nophylock=no). The path that later listened inherited the SNP analog, skipped BMCR when ape-ncsi=yes, used CORECLK_RESET for DMA only, and printed: 

boot: HINT — keep APE PHY (iDRAC NCSI); will not take phylock
boot: HOST-NIC BCM5720 inherit SNP analog; CORECLK_RESET for DMA (skip BMCR)
boot: HOST-NIC BCM5720 ape-nophylock=yes keep-ape-phy=yes ape-lock=yes

That is not a gate close. It is the rule the next two days stood on. Keep APE PHY. Bind LOM :38. Never write the PERC.

Three EPT lessons in one afternoon

Large-RAM iron does not forgive assumptions that QEMU’s -m 512M hid.

  • Pool at 5 GiB. The bump allocator picked the largest conventional span. Guest code lived near 0x1402fd000; identity EPT only maps [0, 512 MiB). Fix: clip the pool into the precise window (v0.1.0-eptfix).
  • No virtio BAR hole. Clipping to 512 MiB filled the whole window; pick_shell_slab_hpa found no unowned 2 MiB leaf above guest RAM. Fix: cap the pool at 256 MiB so [256 MiB, 512 MiB) stays free (v0.1.0-barfix).
  • Host CR3 outside EPT. VMLAUNCH ran; guest shared host CR3 at 0x47e01000 (~1150 MiB). First page-table walk EPT-faulted. Fix: build a guest CR3 that identity-maps the precise window (v0.1.0-cr3fix).
