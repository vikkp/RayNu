The SPA that installed Linux

Mount Everest was never “does it virtualize.” It was one operator loop on a machine we own: ship the EFI, boot the R640, reach a network UI, install a Linux ISO, reboot into that disk. On 11 September 2026, COM2 printed every marker in that sentence.

Phase A had already installed Alpine from --raynu-f (56a3ffd, 10 September). Phase B is the product path: no flag file, no auto-launch. The operator SPA starts RayNu-F.

Coexist, then the Mac could talk

The pin before this one listened and then the Mac got curl: (7). Tight idle was advancing smoltcp Instant ten milliseconds per CPU-speed tick. f72b4276 drives coexist time from TSC. Lease this boot: 10.99.99.145:8443, LOM :38, not iDRAC.

RAYNU-V-M7-PHASE-B-E4-CONTINUE-OK
HOST-NIC coexist listening on 10.99.99.145:8443
RAYNU-V-M7-HOST-NIC-HTTP-OK

Install, then the disk that came back

Alpine 3.21 live, setup-disk -m sys onto virtio vda, then the iron-only line — the one host and CI are forbidden to print:

The installed system’s cmdline still carries the UUID GRUB wrote on the first boot. fsck ran on ext4 vda2 and the FAT ESP. That is E5, started from the SPA, on real iron.

What we claim — and what we don’t

We claim Mount Everest closed on iron. EFI f72b4276 / CI --run 34552377351. We do not claim TLS, leftover-DRAM persist across a hypervisor reboot, a guest VNC console, or cluster features. Those are M8 (ADR-018). vMotion-like work is M9. Overall HDA stays 99% on purpose.

Do not F11 34548550755 / 7f8dc0a9 (curl: (7)) or earlier Phase B fails. This pin is the Phase B reference and the M8.0 rollback kit v0.1.0-everest-closed (EFI SHA256 e74460ff0e248a06d2e4ab546684d1006edd25855f50c8dc27dc202facab9cbc). Do not flash a later persist prototype as the known-good.

2026-09-05 · nested VT-x raynuvsrv1 · ADR-015 / ADR-016 / ADR-017

Please reboot: we became the firmware

Alpine said it first. After setup-disk -m sys packed GRUB and the lts kernel onto a virtio disk we had carved from leftover DRAM, the installer printed the oldest punchline in the book: 

Installation is complete. Please reboot.

Then we actually rebooted it. F7 reset the guest, RayNu-F relaunched against the disk instead of the ISO, GRUB found hd0, and Linux came back with root=UUID= — not the squashfs from the CD. Serial printed RAYNU-V-RAYNU-F-DISK-BOOT-OK. That is a nested victory. It is not Everest E5. Host and CI still never print RAYNU-V-M7-ISO-INSTALL-OK. The Cruzer on the R640 is still too small for alpine-extended. Read this story for the wall we hit, the pivot we made, and why the nested close matters anyway.

What Stage 46 was supposed to be

Everest E5 is one sentence: register a typed Linux ISO, boot its UEFI installer onto virtio-blk, reboot to that disk. Stages 37–43 taught retained OVMF to live on a private VMCS. Stage 44 made the CD answer. Stage 45 booted El Torito on iron. Stage 46 was supposed to be the installer — on the same PowerEdge, over the same COM2. ADR-015 named the close path: park PR #231, stay on #229, do not claim the iron OK from nested, host, or CI.

The iron chase that closed every door except the one that mattered

Product-ISO OVMF on iron would VMLAUNCH, walk past SEC, light DXE, and then sit in CoreWaitForEvent with ataio=0 — the ATA counter never moved. We treated that hang like a PCI mystery, because that is what the last dozen hangs had been.

COMMAND.IO closed: firmware wrote IDE COMMAND six times and ataio stayed 0. CF8 closed: last enable was 00:08.0, still 0. Expansion ROM closed: size probe romwr=0xfffffffe, still 0. Hide slot-0 closed: CDROM-OK via PIIX, still 0. Return address closed: ret=0x7ff0e055 — DxeCore WaitForEvent, not PciBus. ConIn CR closed: we pushed a carriage return; it printed; the hang did not. Callsite closed: call [r14-0x20] into CpuSleep. Each of those pins was a physical Cruzer flash. Mr. COM2 told the truth every time. The disc never started.

WaitForEvent, and the wound we inflicted

The remaining theory was a timer event that never signaled. The remaining tactic — and this is the part we are not proud of — was to make OVMF return. Force the WaitForEvent frame to unwind. Skip the preemption. Poke gState at 0x7ff18340. Inject a page-fault to unstick BDS. 

iron COM2 9474ab6
WFE state4 poke dest=0x7ff18340
then #PF cr2=0xffffffffffffffb8 rip=0x7ff0e018
ataio=0

iron COM2 4e16b59
event #PF inject
OVMF own #PF + CpuDeadLoop
ataio=0

CoreWaitForEvent(N, Events, OUT *Index) must write *Index. The force-return did not. BDS then walked a NULL EFI_EVENT — cmp [r14-0x48],'evnt' — and page-faulted at cr2=0xffffffffffffffb8. The next five pins chased a fault we created. Nested QEMU still reached ATAPI-OK where iron did not: the divergence was timer and interrupt delivery behind our xAPIC/IOAPIC trap, not the boot logic we thought we were debugging.

Two lessons, paid for in flashes:

  • Reaching into another firmware's private state to force it forward is a self-inflicted-wound generator. We do not own OVMF's invariants. Forcing one (a return without its OUT parameter) violates the next twenty.
  • We were reimplementing a PC by trial-and-error, one physical boot per bit of information, to satisfy a third-party firmware whose contract we only partially met.

The pivot: be the firmware

ADR-016 is the adult decision. For the E5 product path, RayNu presents a minimal, correct UEFI boot environment to the ISO's own \EFI\BOOT\BOOTX64.EFI — GRUB, systemd-boot, the Linux EFI stub — instead of relaunching and puppeting OVMF. We author the EFI_SYSTEM_TABLE, the boot services, BlockIo over the CD and the install disk, SimpleFileSystem, LoadImage / StartImage, serial ConIn/ConOut, GetMemoryMap / ExitBootServices, and a timer tick we deliver on our own schedule. Because we author every structure, there is no third-party firmware internal state to corrupt.

RayNu-V is the hypervisor. RayNu-F is the guest boot firmware it presents to a typed ISO. Same single r640-hypervisor.efi. Outside the Proven Core. The 3k–3o OVMF forcing family is gated off (RAYNU_F_NO_FW_STATE_MUTATION). We still refuse to claim the iron installer OK.

Building a UEFI that is ours

The ladder was honest scaffolding first, then nested proof. Byte-exact UEFI 2.10 tables and CRC32. ConOut over a port-0x5246 trampoline. A PE32+ loader with DIR64 relocs. AllocatePages and a coalesced GetMemoryMap whose map-key actually matches ExitBootServices. WaitForEvent that writes *Index and returns EFI_TIMEOUT instead of hanging. Two EFI_BLOCK_IO_PROTOCOL instances: CD 2048-byte read-only from the retained product ISO, install disk 512-byte read-write on virtio-blk. FAT12/16/32, then LoadImage of the ISO's real BOOTX64.EFI.

GRUB ran on our ConOut and complained it could not malloc — so we grew the page pool across pre-mapped report-RAM. Then GRUB loaded Alpine's kernel. Linux 6.12.13 printed efi: EFI v2.10 by RayNu-F. It panicked that a real-mode trampoline was not allocated — we had reserved too much of the first megabyte — so we opened a conventional window [0x1000, 0x9F000). It triple-faulted in efi_enter_virtual_mode — RayNu-F has no runtime services — so the GRUB line grew efi=noruntime. Syscall MSRs were zero at the first usermode helper; we started writing STAR/LSTAR/CSTAR like the G0 path already did. NXE was getting stripped on userspace RIP; we held it after the RayNu-F handoff. None of that is iron. All of it is a firmware we own.

The installer, then the disk that was too small, then the disk that was not

Alpine-standard (245 MiB) reached setup-disk and then apk said there was no dosfstools, no grub-efi. Those packages are not on standard. They are on alpine-extended (994 MiB). The Cruzer in the R640 cannot hold that ISO next to the EFI. Nested can.

On extended, setup-disk finally resolved grub-efi, partitioned /dev/vda, and ran out of space — because the pool disk was 64 MiB with 48 MiB of it ESP. The fix was architectural: carve the install disk from leftover DRAM above the precise EPT window before seeding report-RAM extra. Nested -m 4096M leftover became a 512 MiB virtio disk. Guest never sees those HPAs as RAM (BlockIo only; ADR-004 still holds). 

boot: Stage 46 leftover install disk hpa=0x20000000 bytes=536870912
setup-disk -m sys
25 packages
Generating grub configuration file …
Found linux image: /boot/vmlinuz-lts
Installation is complete. Please reboot.

Nested 499492c completed that install. F7 — reset request, CF9/KBC, disk-before-ISO, then a Vendor whole-disk path so GRUB's hd0 is the install disk — brought Linux back on the second boot (fe4785a). Later 088ab25 switched the F7 reset lines to nowait serial so they still print after Linux shares the UART. That is the nested product loop: ISO → installer → disk → reboot → disk.

What we claim — and what we don’t

We claim a nested RayNu-F alpine-extended install and reboot to that disk, under our own firmware tables, with RAYNU-V-RAYNU-F-DISK-BOOT-OK. We claim Stage 44 and 45 remain closed on real R640 iron. We claim the OVMF forcing family stays off.

We do not claim RAYNU-V-M7-ISO-INSTALL-OK. Nested VT-x is not a PowerEdge. A 512 MiB leftover disk in QEMU is not a Cruzer. Nested sys-install is complete. The iron residual is the same installer on metal — and a stick large enough to hold alpine-extended — plus TLS and guest console. HDA last_commit stays 2b795a0 (P0-14). Months stay 0.5. Prefer under-claiming.

The catalog, then the boot image

Stage 44 got one sector. Stage 45 asked the firmware to treat that disc as a bootable CD. Same afternoon, same COM2, same private VMCS. The serial line grew a new dialect: 

RN-ELT
RAYNU-V-M7-E5-OVMF-ELTORITO-OK
catalog=1 bootimg=1 magic=1 sectors=183 elt=1
packet=533 scsi=0x28 port=0x3f8 com=6
n=197992 insn=ee31c0c3

Read it the way we read ATAPI-OK. catalog=1 means OVMF found the El Torito catalog on the ISO. bootimg=1 means it found the no-emulation boot image. magic=1 is the validation that this is actually a CD boot record, not a hopeful parse. sectors=183 is the boot image itself — a 2048-byte FAT12 ESP with \EFI\BOOT\BOOTX64.EFI, PE SectionAlignment 0x1000. packet=533 is a lot of READ(10). The disc is no longer a single sector of politeness. It is a boot path.

The ladder on COM2 is now a story we can tell without hand-waving. ATAPI-OK at n=30769. Catalog hit around n=33280. Boot image around n=38656. Then the long walk to OVMF-ELTORITO-OK at n=197992. E4 Linux-early and the M4.2 G1 EPT fail-soft still happen on that boot; they are not Stage 45. P0-60 (G1 shell EPT) closed after this stamp. None of that is an installer.

What we still don't claim

Not an installer. Not Everest E5. El Torito on iron means the guest firmware can boot CD EFI. It does not mean Alpine setup-disk ran on the R640, and it does not mean we should keep forcing OVMF's WaitForEvent to get there. That argument is Stage 46.

The CD answers back

Four days ago the guest firmware learned to ask for the CD. Today, on real iron, the CD answered. Two boots, same result: 

RAYNU-V-M7-E5-OVMF-CDROM-OK
RAYNU-V-M7-E5-OVMF-VIRTIO-OK
RAYNU-V-M7-E5-OVMF-BOTH-OK
RAYNU-V-M7-E5-OVMF-ATAPI-OK
boot: guest-UEFI atapi sectors=1 packet=9 scsi=0x28
RAYNU-V-AUDIT: OvmfGuestUefiAtapi exits=30769 sectors=1

Read the last line slowly. scsi=0x28 is READ(10) — the ten-byte SCSI read command that ATAPI packets carry. OVMF, running on its own private VMCS, issued a packet command to the IDE CD at 00:00.1 and got back one real sector. sectors=1. The disc spins up. Data moves.

What it took since Sunday

The iron chase from the last story kept its teeth. Along the way: holding the VGA frame-buffer window write-back while coercing the FIX page to UC so the PAT repaint stopped fighting us; scanning every CpuFlush copy for a jnz that needed to become nop; an ASSERT call-target dump that needed a 32-byte prehex buffer, not 16; and the standing rule from Sunday — do not skip the leave; ret at 0xebecc9c3. Through all of it, 00:00.0 stayed i440FX 8086:1237 so CpuDxe's AcpiTimerLib never ASSERTs, and the virtio disk moved to 00:02.0 to keep the peace.

What we still don't claim

One sector is not an operating system — but it is the firmware reading the disc, on iron, twice in a row. Later the same day, Stage 45 printed OVMF-ELTORITO-OK: the catalog, then the boot image. That story is next. Not an installer. Not Everest E5. Host tests at the close: 480/480.

2026-08-23 · raynuvsrv1 nested VT-x + PowerEdge R640 · ADR-014 Stages 43–44

The firmware asks for the CD

Yesterday left OVMF past SEC with a CD visible and a virtio disk attached. Today the question got sharper: can the guest firmware actually read the disc?

Stage 43: both at once

First the enumeration had to be firmware-simultaneous — OVMF seeing the virtio disk at 00:00.0 and the IDE CD at 00:00.1 in the same boot, not one or the other. A CpuDeadLoop eb f3 skip let PciBus walk 00:00.1, and nested VT-x build 1b07692 printed it: 

pci select 00:00.01  cfg=0x80000100  val=0x70108086
RAYNU-V-M7-E5-OVMF-BOTH-OK
stop n=1111  pci_ide=1 virtio=1  sectors=0

E4 Linux stayed fail-soft through it. Simultaneous enumeration is not a firmware CD boot — but a boot order only means something when the firmware can see both devices at once.

Stage 44: the iron chase

Then the operator loop moved to the R640: build EFI, flash, watch COM2, fix, reflash. What iron taught today:

  • Host owns CR4.OSXSAVE too, and #UD gets intercepted (build 891eb5b) — OVMF's XSETBV may not run bare.
  • Do not skip the leave; ret at 0xebecc9c3 — skipping it let an escaped ASSERT run into a PE header and #UD at 0x109D.
  • CpuDeadLoop is not always dead: the pause; jcc at 0x6e81ca was a preemption artifact, not a halt.
  • The fw_cfg boot order is PIIX ide@1,1 before virtio scsi — and the CD is master drive@0, not slave.

On nested VT-x the same chain now walks past BOTH-OK into ACPI BdsWait — boot device selection. On iron we are chasing the last guest-internal stops.

Where it stands tonight

Stage 44 (RAYNU-V-M7-E5-OVMF-ATAPI-OK) is open. Not an El Torito boot, not an installer, not Everest E5. But the CD is no longer decoration: the firmware is trying to read it.

Update, 2026-08-27: closed on iron — sectors=1, READ(10) answered. The CD answers back.

2026-08-22 → 2026-08-23 · raynuvsrv1 (Ubuntu, nested VT-x) · ADR-014 Stages 36–42

A firmware of its own

Everest E5 is a real distro ISO booting in a guest. Our Linux boots so far came in through the zero-page path we control — no firmware in the middle. A distro installer expects UEFI: OVMF, a CD it can see, a disk it can install to. ADR-014 builds that on a private VMCS — the guest gets its own firmware, its own EPT, its own VMCS, separate from the E4 SHELL path.

The firmware's first act: kill the hypervisor

Stage 37 VMLAUNCHed the retained ESP OVMF.fd on the private VMCS (RAYNU-V-M7-E5-OVMF-VMLAUNCH-OK). Stage 38 found the first wall: OVMF's SEC phase runs mov cr4, 0x640 — which clears VMXE. On a guest that shares CR4 with the host, that is an instant #GP → triple-fault. The fix is the same lesson E4 Linux taught: the host owns CR4.VMXE. With 32 MiB of low RAM and a short resume, OVMF stayed alive past the first triple-fault (RAYNU-V-M7-E5-OVMF-ALIVE-OK).

Past SEC, then a CD and a disk

Stage 39 walked OVMF out of the SEC tail — PEI PCI config, firmware COM, HLT, COM1/COM2 forwarded (RAYNU-V-M7-E5-OVMF-PAST-SEC-OK). Stage 40 made the attached CD guest-visible on PCI IDE/ATAPI (RAYNU-V-M7-E5-OVMF-CDROM-OK). Stage 41 put i440FX and IDE where PEI's Device-ID probe actually looks (00:00.0, DID 0x7010) for the DXE platform boot attempt (RAYNU-V-M7-E5-OVMF-DXE-OK). Stage 42 swapped in an empty virtio-blk disk (DID 0x1042) and set the boot order — CD, then disk: 

RAYNU-V-M7-E5-OVMF-VIRTIO-OK  pci=1 boot=CD,disk  CD GuestVisible
RAYNU-V-M7-E5-OVMF-DXE-OK     plat=1 ram_rip=1

What we still don't claim

This is not a completed firmware CD boot, not an installer, and not Everest E5. No distro has booted. What is true: guest UEFI now runs on its own VMCS, survives its own SEC, and sees both a CD and a virtio disk in the right boot order — the pieces a distro installer will need, closed one gate at a time on nested VT-x before the next iron run.

HTTP/1.1 201 Created
HTTP/1.1 200 OK

Curly quotes in the start URL once hung the Mac in a dquote> prompt. Start-only after that was 404 — VM 1 had not been spec’d. The close used ASCII quotes and both POSTs.

A ladder of EFIs that almost counted

Marker printed is not a close. Several Cruzer flashes proved that the hard way:

  • Hang-fix: first SPA VMLAUNCH then VMPTRLD failed slot=0 and VMXOFF.
  • G0 relocate by memcpy: Linux had scribbled the live VMCS; identity-pool VMPTRLD looped forever.
  • Clone by VMREAD/VMWRITE (98 fields, RIP round-trip): G0 came back; slot 1 VMPTRLD error 11 (wrong VMCS revision).
  • VMCLEAR plus rewrite of the incoming VMCS: error 11 gone; slot 1 re-entry error 7.
  • Drop the incoming rewrite: first SPA RAYNU-V-M7-E4-SPA-LAUNCH-OK, then re-entry with all-zero pin/primary/exit/entry/EPTP/RIP — Intel error 7, invalid control field. Fail-soft parked SPA and kept G0. SDM: do not assume VMCLEAR leaves VMCS data unmodified.

The EFI that closed it (2b795a0) snapshots those 98 fields into a software shadow before VMCLEAR, then VMWRITEs them after VMPTRLD before any clear-state VMLAUNCH. It also punches the SPA 2 MiB slab out of G0’s identity so Linux cannot scribble the parked VMCS.

boot: E4 G0 VMCS relocated HPA=0x0000000010a00000
RAYNU-V-M7-E4-SPA-LAUNCH-OK

boot: E4 restore VMCS shadow slot=00000000 fields=98
boot: E4 SPA VMLAUNCH (VMCS was VMCLEAR; clear-state re-entry)

That pair repeated for many quanta. Paste truncated mid-loop. No error 7. No error 11. No VMXOFF. That is P0-14 / RAYNU-V-M7-E4-SPA-LAUNCH-OK closed on iron. The repeating lines are E4 bring-up debug, not the production console. ADR-011 default is quiet COM2. The next EFI logs the first G0 re-entry, first SPA re-entry, first restore per slot, then stays quiet except HTTP, WARN, and markers.

We claim a private-EPT SHELL guest from SPA start, and that it can leave and come back after VMCLEAR. We do not claim Mount Everest. The SPA guest is SHELL CPUID, not a second Linux, not a distro installer, not TLS. Every switch is still VMLAUNCH (outgoing is VMCLEAR’d), not VMRESUME. HTTP during the switch loop is not in the close paste. Residual is guest console / TLS and a real distro installer. 2026-08-19 · Dell PowerEdge R640 · BCM5720 · APE NCSI

Don’t take the APE PHY

The day before E3b closed, almost every native-NIC EFI printed the same two letters: bmsr=7949 — link down — then skipped listen. COM2 looked busy. The jack had no carrier.

Broadcom’s APE firmware talks NCSI to iDRAC over the same copper the host wants. A Linux-style BMCR_RESET, a PHY lock, or a reset that drops APE’s phylock, and you steal the analog from the BMC. Dedicated iDRAC stays up. Host LOM goes dark. SOL console com2 is not a substitute for a link on :38.

Several Cruzer prefixes are retired for that reason (42b42c99, ec08c00f, 1404f055, skip-CORECLK 26573eb1, and any take-PHY with ape-nophylock=no). The path that later listened inherited the SNP analog, skipped BMCR when ape-ncsi=yes, used CORECLK_RESET for DMA only, and printed: 

boot: HINT — keep APE PHY (iDRAC NCSI); will not take phylock
boot: HOST-NIC BCM5720 inherit SNP analog; CORECLK_RESET for DMA (skip BMCR)
boot: HOST-NIC BCM5720 ape-nophylock=yes keep-ape-phy=yes ape-lock=yes

That is not a gate close. It is the rule the next two days stood on. Keep APE PHY. Bind LOM :38. Never write the PERC.

ADR: ADR-013 · Census: Phase 0 BCM5720 · Tracker: Mount Everest

2026-08-17 · Dell PowerEdge R640 · Cruzer Micro · BIOS 2.2.11

Reality after ExitBootServices

The day after Cruzer stamps closed, we tried to make the management SPA live for the whole boot — not just the 45-second PRE-EBS window. The idea was tidy: park SNP + smoltcp across ExitBootServices (no CloseProtocol), skip the poll that already hung, then listen after BOOT-OK. Firmware would keep owning the NIC. We would keep owning HTTP.

Iron did not care about the diagram.

First EFI: the hang

Poll SNP immediately after EBS and COM2 stops at boot: smoke frame phys=0x1000000. The first iface.poll never returns. Guests never start. That binary (SHA 924af894…) is retired. Do not flash it again.

Second EFI: the timeout, then the red screen

Skip the immediate poll. Guest path comes back — SHELL, M4, BOOTED-FROM-DISK, RAYNU-V-R640-BOOT-OK. Then the idle banner asks the Mac to curl the same lease that worked an hour earlier in the PRE-EBS window (10.99.99.133:8443, MAC b0:26:28:5c:5a:3a): 

boot: mgmt HTTP listening on 10.99.99.133:8443 (POST-EBS SNP idle)
boot: CURL NOW (post-EBS) → http://10.99.99.133:8443/

Same laptop, same LAN, same token: 

curl: (28) Connection timed out after 5002 milliseconds

Then Dell’s red screen: invalid opcode (06), Software UEFI0004 on the BSP, RIP = 0x17 — a jump into garbage. That is not a clean hang. That is firmware taking a pointer we had no right to keep using.

What we still claim — and the ADR that follows

PRE-EBS RAYNU-V-M7-UEFI-HTTP-OK is still true. E2 and E5 stamps are still true. We do not claim RAYNU-V-M7-POST-EBS-HTTP-OK. We do not chase Tcp4 or SNP after EBS.

The same evening Vignesh flashed the WARN-only EFI. COM2 ran through M4.5, printed RAYNU-V-R640-BOOT-OK three times, then: 

boot: WARN — POST-EBS SNP idle skipped; firmware SNP dead after EBS lease=10.99.99.133:8443 (PRE-EBS was the mgmt window; do not chase SNP/Tcp4)

No red screen. That is the close for ADR-013 Phase A on iron. Lifetime management HTTP needs a host-owned NIC (MMIO/DMA) and a dedicated mgmt heap. That architecture is ADR-013 (Accepted). HDA names it E3b. Preserve kit: releases/v0.1.0-adr013-baseline (pre-native-NIC WARN-only idle — not the M8.0 flash; that is v0.1.0-everest-closed). Mount Everest does not close on a 45-second window. Two days later the host-owned NIC listened — see 2026-08-20. The SPA guest that actually launched is 2026-08-21.

First light on PowerEdge R640

For months RayNu-V closed gates on a Latitude laptop under QEMU nested KVM. Mount Everest’s hard gate is different: boot r640-hypervisor.efi on a real R640 and read the markers on serial. Today we closed that gate — loudly, messily, and with the logs still warm.

RAYNU-V-M0-BOOT-OK

That was first light. The screen then sat on M0 with a blinking cursor. ConOut had done its job; ExitBootServices was about to take it away.

The console that wasn’t COM2

HTML5 Virtual Console and BIOS serial redirect show ConOut. Post-M0 RayNu-V prints with port I/O. We had only written COM1 (0x3F8). Dell iDRAC SOL is ssh … then console com2 — COM2 (0x2F8). Same freeze on “serial,” different wire.

Kit v0.1.0-com2 mirrored every host diagnostic byte to both UARTs and added ConOut breadcrumbs through ExitBootServices. Suddenly the story continued: 

boot: M0 complete — entering M1.0 firmware handoff
boot: PE assets embedded (.askern/.asinit) — prefer PE
RAYNU-V-M3-ASSETS-OK
boot: calling ExitBootServices — ConOut/video ends after this line
RAYNU-V-M1-EBS-OK
RAYNU-V-M1-VMXON-OK
RAYNU-V-M3-LOAD-OK
RAYNU-V-M3-BZIMAGE-OK

Three EPT lessons in one afternoon

Large-RAM iron does not forgive assumptions that QEMU’s -m 512M hid.

  • Pool at 5 GiB. The bump allocator picked the largest conventional span. Guest code lived near 0x1402fd000; identity EPT only maps [0, 512 MiB). Fix: clip the pool into the precise window (v0.1.0-eptfix).
  • No virtio BAR hole. Clipping to 512 MiB filled the whole window; pick_shell_slab_hpa found no unowned 2 MiB leaf above guest RAM. Fix: cap the pool at 256 MiB so [256 MiB, 512 MiB) stays free (v0.1.0-barfix).
  • Host CR3 outside EPT. VMLAUNCH ran; guest shared host CR3 at 0x47e01000 (~1150 MiB). First page-table walk EPT-faulted. Fix: build a guest CR3 that identity-maps the precise window (v0.1.0-cr3fix). 
boot: frame pool clipped to guest RAM [1MiB,256MiB); BAR/shell window free
boot: M4.3 virtio-blk BAR=0x10000000
boot: VMLAUNCH → guest store+loop+HLT + IRQ inject (EPT)
boot: ERROR — EPT violation GPA=0x47e01000
boot: guest rip=0x1007000  cr3=0x47e01000

That was mid-afternoon edge: BAR window correct, guest RIP in-window, CR3 still the UEFI table high in DRAM. The rest of the day was the ladder — host CR3, RIP-relative GPRs, INVPCID, keep earlyprintk, then Enable XSAVES — until /init stopped eating its own stack.
