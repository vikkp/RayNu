After Everest, in the order the iron will bear

The loop closed on a real PowerEdge on 11 September. The twenty-three days since then put Guests on the PERC spare, logged in from an 8 GiB window and a 10 GiB tail, and stored an unmodified Ubuntu ISO. They did not boot that ISO, and they did not retire one line of the Alpine patcher. The months below are that pace.

Chapter 1 · October 2026

The ISO the operator chose

  1. This boot

    M8.8.3 — the PERC ISO is the CD

    Guests shows the 8 GiB Alpine, the 10 GiB Alpine, and the waiting ISO. The ISO button publishes vdb and loads \EFI\BOOT\BOOTX64.EFI from that file. The previous boot attached the file as vdb and still started the Cruzer Alpine image.

  2. October

    See the installer

    The kernel line is still the one stored in the Ubuntu file. console=ttyS0 is not injected, and the stored bytes stay unchanged. Subiquity is the close, on the serial line or on a framebuffer the firmware actually provides.

  3. October

    M8.8.4 — install, then Clear ISO

    Subiquity writes the new tail disk. The file stays until Guests presses Clear ISO. That click wipes the signature sector. The 8 GiB window, ee851fd5, and UBUNTU0 stay.

  4. After the disk boots

    Guest SSH on the other LOM port

    A virtio NIC with its own MAC. Frames leave 01:00.1. The SPA stays on the port it already has. Customer DHCP, or an address they set. Recorded, not built.

Chapter 2 · October through December 2026

Letter of intent, two bars

Bar A · 92% · October

Dedicated box

One PowerEdge they can spare. Everest, the SKU card, TLS, and a standing SPA are done. Persist has repeated. The keyboard lived once. Auth beyond the lab latch is parked on purpose. The conversation window is this month. The score does not go to 100 while that latch is the product default.

Bar B · 60% · December

RAID fleet

The buyer already keeps disks on a PERC. The close is a login from the spare virtual disk, not from an 8 GiB or 10 GiB slice cut out of it. The tracker holds 1.5 months. A Ubuntu install that stays on a 10 GiB tail leaves December where it is, and the date slips into 2027 if the slice is still the disk in December.

  • M8.2 Operator auth. Host package exists. The chassis still answers the bring-up token. Piece score 38.
  • M8.5 UEFI catalog persist. The firmware write is still the open half. It sits beside the ISO work. It does not block the October boot.
  • M8.6 Windows and the later distros. Same UEFI plus virtio shape. It waits on Generation 1 runtime services. It is phase 5, not this quarter.

Chapter 3 · late 2026 through 2027

RayNu-F, Generation 1

One firmware, one virtual machine, unmodified media. The last twenty-three days closed operator slices and left every Generation 1 phase except a patched Alpine reboot unstarted. The quarter-per-phase spacing is that fact. ADR-020 set the phases. This page is the first place they have months.

  1. Oct–Nov 2026

    Phase 0 — stop adding Alpine glue

    Half closed. Iron already rebooted a patched Alpine disk to a login. The other half is freezing the patcher and the auto-answer behind the lab path. No new guest-side patch on the product ISO.

  2. Nov 2026 – Jan 2027

    Phase 1 — split the monolith

    guest_uefi.rs becomes the exit loop, one module per Generation 1 device, and raynu_f/. Alpine install on iron still passes. The OVMF launch path comes out.

  3. Q1 2027

    Phase 2 — devices that make the knobs unnecessary

    PIIX goes. Timers keep time. The console is chosen once, serial or a linear framebuffer. CPUID, ACPI, and SMBIOS match the contract. Virtio is modern only: block, net, console, rng. A stock Alpine extended ISO reaches login: with the grub.cfg as shipped. The patcher is deleted. This is the first unmodified-media close.

  4. Q2 2027

    Phase 3 — runtime services

    Variable store, ResetSystem, GetTime, and SetVirtualAddressMap through the guest page tables. Ubuntu Server and Debian netinst reach their installers with efi=noruntime absent. A missing service prints the service name.

  5. Q3 2027

    Phase 4 — freeze v1.0

    One document: CPUID, memory map, PCI addresses, ACPI, SMBIOS, console, and the refusals. CI installs Alpine extended, Ubuntu Server, Debian netinst, and Rocky, reboots each to its disk, and reaches a login. VM config carries generation 1.

  6. Late 2027 – 2028

    Phase 5 — after the freeze

    Secure Boot, a virtual TPM, firmware-phase SMP, HTTP and PXE boot, Windows, and the UEFI self-certification tests as an outside oracle. None of these is a v1.0 exit. Windows is M8.6 landing here, once runtime services exist.

Chapter 4 · 2028 sketch

Hot-add, and the cluster that waits for it

ADR-018 moved this off M8. A single host that still patches Alpine is the wrong place to add a CPU to a running guest. The start line is Generation 1 frozen and one unmodified install lived on the spare.

M9

Hot-add

CPU and memory on a running guest. The firmware has to advertise the slots before the OS will take them. That advertisement is a Generation 1 contract, which is why this sits after phase 4.

M9

Live migrate

A vMotion-shaped move of one guest. The page-transfer proof work from M6 stays substrate. It is not a second host, and it does not start while the ISO chapter is open.

M9

Placement

A DRS-shaped choice of where a guest runs. It needs more than one RayNu-V host that already boots the same generation. One R640 is the whole lab today.

How to read this

Under-claim, then move the month when COM2 agrees

October is busy on purpose: the ISO boot, the installer, Clear ISO, guest SSH, and the Bar A window share it. December is Bar B only if the guest disk stops being a slice. 2027 is RayNu-F. 2028 is hot-add and the cluster sketch. If a quarter produces another operator slice and no firmware phase, the Generation 1 bars slide right and the page says so.
