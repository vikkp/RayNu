# ADR-021: The professional-grade bar — Shipment 1 and the final SKU

- **Status:** Accepted as the bar and the catalog. Nothing in the catalog is claimed by this ADR; each row carries its own status.
- **Date:** 2026-10-19
- **Pillars:** [Z] single binary · [D] iDRAC-native · [A] audit-first · [V] architecture preserved (no Proven Core expansion)
- **Parent:** [ADR-018](ADR-018.md) (M8 operator hardening) · [ADR-013](ADR-013.md) Appendix C (guest egress) · [ADR-014](ADR-014.md) (typed ISO) · [ADR-019](ADR-019.md) (Guests screen) · [ADR-020](ADR-020.md) (VM Generation 1)
- **Does not change:** Proven Core boundary (ADR-002), size budget (ADR-003), iron-only markers, the M8 gate order in [`docs/m8_plan.md`](../m8_plan.md), the M9 number for cluster.
- **Public copy:** [`site/sku.html`](../../site/sku.html) renders [`site/sku.json`](../../site/sku.json), which `./tools/sync-sku-site.sh` generates from the **Catalog** section of this file. CI runs `--check`. Edit the tables here, not the JSON.

## Context

On 2026-10-19 the installed Ubuntu guest on the R640 brought `enp0s5` up, transmitted 15 frames on `:39`, received none, and `ip neigh` said `10.99.99.1 FAILED`. iDRAC had the answer the whole time: Integrated NIC port 4 (`B0:26:28:5C:5A:39`) was **Link Down**, auto-negotiation **Disabled**; port 3 (`:38`, the SPA) was Up at 1000 Mbps. The hypervisor had armed rings and set `MAC_MODE` on a PHY it never looked at, the SPA showed a guest with a NIC and no sign that its uplink had no cable, and the egress port is selected by comparing against one MAC constant that is this lab's. Fixing the PHY is [PR #409](https://github.com/vikkp/RayNu/pull/409). The lesson is wider than one port.

The operator then asked the product question: *does RayNu-V always need two cabled ports, and what do we tell an R640 customer to plug in?* The honest answer is "today, yes: iDRAC, port 3 for the SPA, port 4 for guests, all untagged" and that is a reasonable default (ESXi best practice separates management from VM traffic). But it exposed that the project has never written down, in one place, **what a professional operator expects from a hypervisor they run unattended**, which of those things RayNu-V has lived on iron, which are in flight, and which are only named. [`docs/sku.md`](../sku.md) and `site/sku.html` describe what an LOI holds *today*. [`docs/m8_plan.md`](../m8_plan.md) lists the next nine gates. The M9 sketch has three rows. None of them is the list a buyer compares against ESXi, Proxmox, or Hyper-V.

Known gaps that surfaced on iron this month and are not on any plan yet:

- The guest uplink is hardcoded to `EGRESS_PHY_MAC` (`…:39`). Another R640 has another MAC. Egress must discover the second BCM5720 function.
- Physical link state of either LOM port is invisible in the SPA. A guest with `RX 0` should read "uplink: no link" on Guests, with an audit event when it changes.
- The saved vNIC is RAM-only; the operator re-saves it every boot. SPA state does not survive a host reboot (M8.5 names this for the catalog; it is wider).
- The virtio-net device always reports carrier up. Linux `carrier=1` while the wire is dark.
- Shared-LOM iDRAC (one cable) versus dedicated iDRAC is supported by accident, not by a documented matrix.
- Stop kills the guest. There is no ACPI power button, so no clean shutdown from the page.
- Guests do not start on host boot. A power cut leaves the operator at the SPA pressing Start.
- The host has no NTP, no static address, no DNS of its own. The SPA address is whatever DHCP gave `:38`.
- The hypervisor is updated by flashing a USB stick (`F11`). There is no in-place update and no rollback from the page.
- The EFI is unsigned. R640s ship with Secure Boot available; a customer who turns it on cannot boot RayNu-V.

## Decision

1. **Define the bar.** A professional-grade hypervisor is one a trained operator can install from a document, run unattended for months, update without a rack visit, recover from a power cut without typing, and audit after the fact. The catalog below is that bar for a Dell PowerEdge single host, plus the cluster and migration rows that complete the product RayNu-V set out to be. It is deliberately longer than any one milestone.

2. **Two shipments, one catalog.** Every capability in the catalog is in the **final SKU**. A subset is marked **S1**: what **Shipment 1** (the dedicated-box letter) ships. S1 is the set without which a customer cannot run one Ubuntu guest on one R640 without the RayNu-V team in the room. Everything not S1 ships later; the catalog still names it so the website can publish what is planned, not only what exists.

3. **Status vocabulary** (per row, no other words):
   - **lived** — printed on the R640 (or, where the row is a host artifact, closed in CI) with a commit SHA in the Note. Latitude/QEMU do not make a row lived.
   - **in flight** — code exists on a branch or PR and is under iron test. Named in the Note.
   - **planned** — accepted by this ADR, not built. A planned row has no evidence and claims none.
   Promotion to **lived** requires the evidence rule above. Demotion is allowed and must be recorded in the HDA changelog.

4. **The catalog is the single source.** `./tools/sync-sku-site.sh` parses the H3 areas and their tables into `site/sku.json`; `site/sku.js` renders it; CI runs `./tools/sync-sku-site.sh --check`. The `docs/sku.md` card and `site/sku.html` copy describe Shipment 1 and the final SKU; neither carries its own list.

5. **Order of work stays [ADR-018](ADR-018.md).** This catalog does not reorder M8.0–M8.9 and does not pull M9 forward. New S1 rows that are not already an M8 gate (uplink discovery, link state, clean shutdown, autostart, host NTP/static address, config persist, signed EFI, in-place update, headless operation) are appended to the M8 plan as **M8.10 and later** when their predecessor closes, in the order they appear here.

6. **Proven Core unchanged.** Nothing in this catalog enters the Proven Core. Rows that touch it (CPUID/MSR firewall, EPT isolation, allocator) are verification rows and are already inside.

7. **What is outside even the final SKU.** No userspace, no shell on the host, no package manager, no KVM/Xen/bhyve lineage, no feature parity with ESXi on day one, no Tier 2 iDRAC dependency as a shipping blocker (ADR-005). Any of these would need its own ADR.

## Build order (the rule behind decision 5)

Accepted 2026-10-19. The catalog letters are a reading order for a buyer; they are **not** the build order. Dependencies cross letters (autostart B5 needs config persist C8; in-place update A7 must not wipe guests, so it needs C8 too; link state D5 needs a working uplink D3), the R640 is one machine with one operator, and building area A first would delay the one thing that proves the product, a guest on the customer's LAN.

The order is **waves**. Each wave ends with something visible on the SPA. Every catalog row is in exactly one wave. `./tools/sync-sku-site.sh` validates that, writes the wave onto each row in `site/sku.json`, computes the **current wave** (the lowest numbered wave with a row that is not yet lived), and `./tools/sync-sku-site.sh --next` prints what to pick up.

**Rules.**

1. **One iron thread at a time.** Each wave names exactly one row that needs the R640 (the *Iron thread* column). Everything else in the wave is host-tested and waits for that one confirming boot. Do not open a second iron thread while the first is unclosed.
2. **Host-only rows are filler, always available.** When the rack is waiting on a cable, a teammate, or a flash, pick the next non-lived host-first row in the current wave; if none, the next host-first row in the next wave. Never idle the engineer on the rack.
3. **A wave closes when every row in it is lived.** Then the current wave advances by itself in `sku.json`. No ceremony beyond editing the row's status with evidence and running the sync.
4. **Final rows do not jump the queue** because a prospect asks. The honest answer is the SKU page. Verification rows (wave V) are the exception in the other direction: they run continuously on the side and never wait for a wave.
5. **Wave 9 is not optional.** A 72-hour soak on the real R640 is what turns 67 rows into Shipment 1.

**When a gate passes** (an iron marker prints, or a host gate closes): in the same change, (a) set that row to `lived` with the SHA or marker in its Note, (b) run `./tools/sync-sku-site.sh` and stage `site/sku.json`, (c) run `./tools/sync-sku-site.sh --next` and start the first row it prints, (d) if the wave closed, say so in the HDA changelog. The rule file is [`.cursor/rules/build-order.mdc`](../../.cursor/rules/build-order.mdc).

## Shipment 1 in one paragraph

One `r640-hypervisor.efi`, signed, booted from iDRAC virtual media or USB on a PowerEdge R640. The operator reaches an HTTPS page with their own certificate and their own account, on a management port with a static address they chose. They upload an Ubuntu ISO, create a guest with the CPUs, RAM and disk they want on the PERC array they already own, attach a NIC, and the SPA shows them that the guest uplink has link before they press Start. The guest installs, reboots to its disk, gets an address on the customer's network, and they SSH to it from their desk. They can type into it from the browser when SSH is not an option. When the rack loses power the guest comes back on its own. When a new RayNu-V ships they update from the page and roll back from the page. Every one of those actions is in an audit log they can export. Nothing in that paragraph requires COM2.

## Consequences

- The website can publish two honest lists: Shipment 1 and the final SKU, with lived / in flight / planned on every row, generated from this file. Changing a status is a commit to this ADR with evidence, reviewed like code.
- Counting the catalog is not a score. HDA stays the distance tracker; overall stays **99%** for Everest and does not become a catalog percentage. The SKU page shows counts, not a percent-to-GA.
- Several S1 rows are new work not in the M8 plan. They are appended as M8.10+ when their predecessor closes (decision 5). They do not block M8.9.
- `docs/sku.md` and the `site/sku.html` copy stop carrying their own list of what ships. They describe the two shipments and point here.
- `tools/check-site-chrome.sh` requires `site/sku.html`, `site/sku.js` and `site/sku.json`; `tools/sync-sku-site.sh --check` runs in the same CI jobs as the HDA sync.
