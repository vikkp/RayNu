# ADR-024: Guest vCPUs on host cores — one monitor lock, a run queue per core

- **Status:** Accepted. In flight on branch `cursor/wave-7-b21-host-cores-25ca`. Gate 1 lived on iron `dc1bcc800c1e` (16 cores online, vCPUs still on core 0). Gate 2 in progress on iron `b47e029d88aa` / run `44622224710`: `boot: B21 vcpu 1 on host core 1`, `cores 0:[0.0] 1:[0.1]`, `Brought up 1 node, 2 CPUs`, `raynusrv2 login:`, SPA loaded, `ssh` to `10.99.99.200`, `nproc` printed `2`. That is not the section 9 pass. Steps 2–5 and 7 are not run. vCPU 0 stayed on core 0. Gate 3 is not started. Not lived. B22 is planned, not built.
- **Date:** 2026-11-18
- **Pillars:** [D] Dell cores we own · [Z] still one binary · [V] architecture (one lock, explicit home cores) · [A] `VmxEnabled` once per core
- **Parent:** [ADR-023](ADR-023.md) (what B21 changes) · [ADR-022](ADR-022.md) · [ADR-021](ADR-021.md) rows B21 and B22 · [ADR-016](ADR-016.md) · [ADR-002](ADR-002.md)
- **Does not change:** the Proven Core. No Proven Core file is edited. `VmxLifecycle` is instantiated once per host core. `AuditEvent::VmxEnabled { vcpu_id }` is reused with the core index.

## Context

B7, lived on iron `505ef6bdbc73`, gives a guest N CPUs on one host core. The other cores of the R640 stay where the firmware parked them. `vmx/guest_uefi.rs` has on the order of 225 statics written for that one CPU, and the VM-exit landing stores the guest registers into globals (`SAVED_RAX`, `SAVED_XMM`). A second core that ran that path at the same time would corrupt the first.

B21 starts the other host cores, puts each one in VMX root, and runs vCPUs on them. A guest with 2 vCPUs then has two cores of capacity. A guest cannot be given more vCPUs than there are host cores online, except on the one-core path, which stays the lived B7 machine (cap 4).

The owner's rule for the row: do it slow, do it right. Three iron gates, in order. A failed gate stops the line.

## Benchmark

How ESXi does it, and where this row differs. The owner set the benchmark on 2026-11-17; the differences were accepted with the plan.

| ESXi | B21 | Same? |
|---|---|---|
| Every host logical CPU runs the scheduler; a vCPU runs on any of them | A run queue per host core; a vCPU is placed on a core when it comes up | Yes, without later rebalancing (B22) |
| A VM cannot have more vCPUs than host logical CPUs | `cpu_max = min(4, host cores online)` once more than one core is online; Save and Start refuse more | Yes |
| A halted vCPU gives up its CPU; an idle CPU sleeps | A core with no vCPU sleeps in MWAIT; a core whose vCPUs are all halted polls | Partly. The halted core spins (B22) |
| A vCPU on another CPU is interrupted with an IPI | Host IPI on vector `0xF2` forces the VM exit | Yes |
| No two VMs on sibling hyperthreads | One thread per physical core is started. The sibling is never used | Yes, the strict form |
| The kernel is finely locked; many CPUs are in the kernel at once | One monitor lock. Guests run in parallel. Hypervisor work is one core at a time | No. Stated. B22 splits the lock |
| Co-stop bounds sibling drift | Not built. At one vCPU per core there is nothing to bound | Not needed at 1:1 |

## Decision

| # | Decision |
|---|---|
| D1 | One monitor lock. After a core is online, every instruction it runs in VMX root that touches shared state runs under one fair ticket spinlock. Taken in the VM-exit landing stub before any guest register is stored. Released by the VM-entry stubs after the last register is loaded. |
| D2 | With one host core online, behaviour is B7 as lived. The only instructions that differ are the uncontended lock take and release and one COM2 summary line. A machine with one core online keeps the B7 vCPU cap of 4. The `min(4, cores)` cap applies once more than one core is online. |
| D3 | Core 0 is the home core. Boot, the E4 idle loops, Start, the RayNu-F firmware phase, reset, leave, guest INIT/SIPI service and the management tick run only on core 0. The other cores run vCPUs and nothing else. Core 0 holds at least one vCPU whenever any guest is on. |
| D4 | A run queue per core. The lived `pick` runs on each. Each unit (`slot * MAX_VCPUS + vcpu`) is assigned to exactly one core, when it comes up: fewest units, a non-zero core before core 0 on a tie, then the lowest index. Revisited only when core 0 switches a unit out (offload) and when core 0 recalls a unit. No move between two non-zero cores. |
| D5 | A VMCS has a home core. Only that core may load, read, write or clear it. A move: the home core VMCLEARs it; the new core VMPTRLDs it, writes `HOST_RSP` for its own stack, and enters with VMLAUNCH. |
| D6 | Only core 0 asks another core for a unit and waits (recall). A non-zero core never waits on another core for a unit. Any core may wait for other cores to take a pending INVEPT, and that wait is only on cores that are in guest mode. |
| D7 | The kick is a host IPI on vector `0xF2`. External-interrupt exiting and ack-on-exit are already set, and host IF is always 0, so a kick is a VM exit and never a host interrupt. Correctness never depends on a kick: a running vCPU exits at least every 2 ms, a parked one is polled every 200 µs. `EFI\RayNu\nokick.txt` turns kicks off. |
| D8 | A core with no unit sleeps in MWAIT (C1) on its mailbox word, or PAUSE when CPUID has no MWAIT. A core whose units are all halted leaves the monitor and polls every 200 µs. Core 0 is unchanged: it spins through exits, and that is what ticks the page. |
| D9 | One thread per physical core. Hyperthread siblings are never started. At most 16 cores (`MAX_UNITS`). |
| D10 | GDT, TSS, IDT, CR3 and the control registers are core 0's. Per core: a 1 MiB host stack and a VMXON region. |
| D11 | `guest_cpu::cpu_max()` returns `min(MAX_VCPUS, host cores online)` when more than one core is online, and `MAX_VCPUS` when one core is online or `EFI\RayNu\onecore.txt` is present. Save refuses a larger count. Start of a row whose saved count is larger is refused with a sentence that names both numbers. `onecore.txt` starts no other core. |
| D12 | Platform timers stay on vCPU 0's exits, on whichever core vCPU 0 runs. A host timer is B9. |
| D13 | Three iron gates, one branch. Gate 1: cores online, guests still on core 0. Gate 2: vCPUs 1..N on other cores. Gate 3: a guest's vCPU 0 on another core. The row is lived at gate 3. |
| D14 | No Proven Core file is edited. |
| D15 | Topology comes from EFI MP Services (`uefi` 0.33 `MpServices`, GUID `3fdda605-a76e-4f46-ad29-12f4531b3d08`) before ExitBootServices. Cores are started after ExitBootServices with INIT, SIPI, SIPI. No MADT parse. Protocol absent means one core and a COM2 line. |
| D16 | A panic keeps the monitor. The panicking core does not release the lock, so every other core stops at its next exit. |
| D17 | A value read from guest memory that decides a host-side bound, index or address is read once into a local and validated there. |

## Deviations from the ADR-023 table

ADR-023's "What B21 changes" column was the starting point. Where that table and this ADR differ, this ADR is the decision.

| ADR-023 said | ADR-024 does |
|---|---|
| One lock per guest around device emulation | One monitor lock around all of VMX root. Per-guest locks are B22. |
| One host stack, GDT, TSS and VMXON region per host core | One host stack and one VMXON region per core. GDT, TSS and IDT stay core 0's. The host takes no interrupts and has no IST stacks, so a per-core TSS would have no reader. The row that installs a host IDT brings the per-core TSS. |
| A ready queue per core, and co-stop | A run queue per core. No co-stop. No rebalance after a guest leaves. |
| Platform timers driven by one host timer | Still driven by vCPU 0's exits. B9. |
| `cpu_max = min(4, cores online)` with no exception | That formula once more than one core is online. One core online, and `onecore.txt`, keep the B7 cap of 4 so the lived machine does not change. |

## Known limits

- Hypervisor work runs on one core at a time. A long operation on core 0 (guest Start, RAM zeroing, a TLS handshake, PERC I/O) delays every other vCPU's exits for that long. B7 had the same stall for every guest. B21 does not make it worse. B22 removes it, using the lock-wait numbers this row prints.
- Placement is decided when a vCPU comes up. After a guest leaves, units are not rebalanced between non-zero cores. With more units than cores, cores are shared with the 2 ms quantum and there is no co-stop.
- A core whose vCPUs are all halted spins outside the monitor. Core 0 always spins. Deeper C-states are not used.
- Hyperthread siblings are not used.
- GDT, TSS and IDT are shared. A host fault is fatal, as today.
- Platform timers are still stepped by vCPU 0's exits. B9.
- The ACPI PM timer at port `0xB008` steps `0x0040_0000` on every read (`devices/guest_platform.rs` `tick_pm_timer`). That step is unchanged since B7 `505ef6bd`. On `b47e029d` Linux printed `PM-Timer had inconsistent results: 0xc00000, 0x800000 - aborting.` Those two samples are one step apart the wrong way: the shared counter moved, wrapped the 24-bit range, and the second vCPU's reads landed in between, so the later sample is `0x800000` rather than a small wrap residue. Linux accepts a wrap only when the second value is below `0xFFF`. No change here. A stable guest clock is B9.
- `guest_tsc()` over-counts time away for a guest whose cores are shared.
- Not more than 16 host cores. No MADT fallback when MP Services is absent.
- A core whose `rdtsc` is a constant offset from core 0 has that offset added to its `IA32_TSC_ADJUST` once. Three later samples must fall within 1 ms, or the core is not used. Iron `a9301533682b` printed `online=1 of 16` when equal offsets were required; the guest on core 0 still reached `nproc` 2.
- Only core 0 panics are exercised by the page button.
- A kick left pending on core 0 after the last guest stops is taken by the next guest entry on core 0.

## Guest memory review

Reviewed before a second vCPU runs beside the first (plan section 5, WP8). The list of sites, the verdict, and each fix is [`docs/reviews/b21-d17-guest-memory.md`](../reviews/b21-d17-guest-memory.md).

`process_blk_queue` rejects a descriptor whose `next` is at or past the queue size, and fails a request whose data-descriptor lengths sum to more than `MAX_REQ_BYTES` (8 MiB) without copying that buffer. The virtio-net walks no longer fold an out-of-range `next` into the ring with a remainder. There is no virtio-console device in the tree.

## Consequences

- Guests run in parallel. Hypervisor work runs one core at a time.
- The row is not lived until gate 3 on the R640: two busy guests each keep a full core, and B6 and B7 still work on the same stick. Nested QEMU and CI do not close it.
- `EFI\RayNu\onecore.txt` is the on-stick way back to B7 behaviour. Rollback sticks stay `505ef6bdbc73` / run `44336344309`, then GitHub Latest `v0.1.7-b6`.
- Scores stay put. HDA overall stays 99%.
