# ADR-017: Guest reset under RayNu-F (F7)

- **Status:** Accepted
- **Date:** 2026-09-05
- **Pillars:** [Z] single binary · [A] audit ([V] architecture preserved — no Proven Core expansion)
- **Parent:** [ADR-016](ADR-016.md) (RayNu-F) · [ADR-014](ADR-014.md) (typed ISO / UEFI+virtio) · [ADR-009](ADR-009.md) (Mount Everest E5)
- **Does not change:** Proven Core boundary (ADR-002), size budget (ADR-003), iron `RAYNU-V-M7-ISO-INSTALL-OK` (still iron-only)

## Context

Nested `499492c` on `raynuvsrv1` completed Alpine `setup-disk -m sys` onto a
RAM-backed virtio-blk disk under RayNu-F. The guest parked at `localhost:~#`
with `Installation is complete. Please reboot.` Nothing sent `reboot`. A
Linux reset request had nowhere to go: no FADT `RESET_REG`, KBC `0xFE` was
absorbed, `0xCF9` was generic I/O, and a triple fault after handoff was a
fatal `raynu_f_stop`.

Everest E5 still requires **install to virtio-blk then boot the installed
disk**. F7 is that reboot path under RayNu-F. Nested QEMU is not R640; F7
does not close E5.

## Decision

1. **Architected reset inputs only.** Recognise Linux `reboot=` as:
   - I/O `OUT` to `0xCF9` with bit 2 set (`0x04` / `0x06` / `0x0E`),
   - KBC `OUT` `0x64` value `0xFE`,
   - triple fault after a pending request (Linux tried KBC/CF9 then faulted).
   Publish `RESET_REG` (SystemIO, 8-bit, `0xCF9`) + `RESET_VALUE = 0x06` and
   `FADT.flags |= RESET_REG_SUP` so the default `reboot=acpi` path hits `0xCF9`.
   Do not mutate Linux or GRUB internals to force a reboot.

2. **Relaunch RayNu-F; keep the install disk.** `raynu_f_reset_relaunch`
   resets firmware/device state, zeroes the low-RAM slab, rewrites VMCS guest
   state for long-mode entry, and calls `raynu_f_launch_on_stopped_vmcs`.
   `guest_virtio_blk::reset_keep_disk` clears virtio PCI/queue state and
   **keeps** `DISK_HPA` / `DISK_LEN` / `BYTES_WRITTEN` and the retained ISO.
   **Do not** call `guest_virtio_blk::reset()` on this path — that zeroes the
   disk. Do not call `ide_cdrom::reset()` — the product-ISO window stays armed.

3. **Boot order is disk-before-ISO.** `raynu_f_boot_source(disk_has_gpt_esp)`
   prefers a GPT ESP on the install disk (`\EFI\BOOT\BOOTX64.EFI`, fallback
   `\EFI\alpine\grubx64.efi`). First boot the disk is zeros (`attach_disk`
   zeroes it), so El Torito still wins. Print
   `RAYNU-V-RAYNU-F-DISK-BOOT-OK` only when StartImage ran an image staged
   from the disk ESP. Never print `RAYNU-V-M7-ISO-INSTALL-OK` or reuse
   `RAYNU-V-M7-ISO-BOOTED-FROM-DISK`.

   `HANDLE_DISK` BlockIo is the **whole disk** (`MEDIA_LOGICAL_PARTITION=0`).
   Its device path is Hardware/Vendor (`GUID_RAYNU_F_DISK`), **not** a
   Media/HardDrive partition node. GRUB `efidisk` skips HD/CDROM nodes as
   partition children that need a parent; an HD node on `HANDLE_DISK` made
   nested `3492ebc` print `disk `,gpt2' not found` / `grub rescue>` after
   F7 relaunch (prefix `(hd0,gpt2)` collapsed to `,gpt2`). `encode_hd_device_path`
   stays for tests / a future partition handle. SFS on `HANDLE_DISK` still
   mounts the ESP FAT via `fat_volume_off`.

4. **Reset cap is 1.** `RAYNU_F_RESET_MAX = 1`. A second request stops with
   reason `reset-cap` so a boot loop cannot spin.

5. **Serial drive.** After `Please reboot.` and the next shell prompt, enqueue
   `reboot` once. After relaunch, answer the second `login:` with `root` and
   never send `SETUP` again (that would wipe the install). `KERNELOPTS` on
   the first-boot `SETUP` line carries the RayNu-F Linux knobs so installed
   GRUB inherits them (`setup-disk` honours `KERNELOPTS`).

6. **Outside Proven Core.** Devices, RayNu-F, and `vmx/guest_uefi.rs`
   guest-firmware emulation stay outside. No EPT / VMCS-encoding / allocator
   changes.

## Consequences

- Nested evidence of a second `Linux version` + `root=UUID=` is required
  before claiming reboot-to-disk. Host tests cover GPT/ESP, HD vs whole-disk
  device path (GRUB partition-child skip), reset classifier, `reset_keep_disk`,
  serial `reboot` / second-boot, FADT reset register, and marker stability.
  Nested `3492ebc` reached disk GRUB then rescue (`gpt2`); whole-disk path
  is host-wired and awaits a nested rerun. VMCS re-init after 64-bit Linux
  and the installed GRUB cmdline remain nested-only risks.
- Iron `ISO-INSTALL-OK` still needs a stick large enough for alpine-extended
  (Cruzer 977.5 MiB cannot hold it).
- HDA months stay 0.5 until nested (then iron) evidence; nested-only does not
  drop months.
