# ADR-023: N virtual CPUs per guest slot, time-sliced on one host core

- **Status:** Accepted. Lived on iron `505ef6bdbc73` / run `44336344309` (2026-11-18). B21 is planned, not built.
- **Date:** 2026-11-17
- **Pillars:** [Z] single binary · [V] architecture (one schedulable unit per vCPU, explicit banks) · [A] a vCPU-count save is an audit event
- **Parent:** [ADR-021](ADR-021.md) rows B7 and B21 · [ADR-022](ADR-022.md) (one guest model, N slots) · [ADR-020](ADR-020.md) (RayNu VM Generation 1) · [ADR-016](ADR-016.md) (RayNu-F)
- **Does not change:** Proven Core boundary (ADR-002), except one new audit-event variant `GuestCpuSaved` (tag 82) in `audit/integrity.rs`, the same shape as tags 76–81. No guest firmware state is forced (ADR-016). No VPID, no APICv, no x2APIC.

## Context

A product guest started from the Guests page has one CPU. Linux on metal brings extra CPUs up with INIT, then a startup IPI. ADR-021 B7 is that guest-visible CPU count: N = 1..4, chosen per Guests row, default 1.

The hypervisor still runs on **one host core**. The N vCPUs of a guest are time-sliced on it by the guest scheduler, the same way two guests are today (ADR-022). B7 adds no throughput. It adds the guest-visible CPU count, IPIs, per-CPU LAPIC timers and interrupt destination routing.

The row closes when an Ubuntu product guest on the R640 reports more than one CPU over SSH (`nproc`), with B6 behaviour unchanged.

Running vCPUs on more than one host core (host AP bring-up, VMXON per core, per-CPU host state, locks on the single-CPU statics) is not B7. That is catalog row **B21**, Shipment 1, in wave 7 directly after B7. The owner confirmed on 2026-11-17: move B21 to Shipment 1; the soak can wait; do it slow but do it right. The wave 9 soak runs after B21, on a build where vCPUs have real cores.

ADR-021's Shipment 1 paragraph already promises a guest with the CPUs, RAM and disk they want, and an audit log of every one of those actions. ADR-022 names the one-core split as what the later CPU rows are for.

## Benchmark: VMware ESXi

How ESXi does it (owner, 2026-11-17):

- Every vCPU is a *world*, a schedulable context of its own. A 4-vCPU VM is four worlds. ESXi places worlds on any host logical CPU and moves them. A world that halts gives its CPU away.
- A VM cannot have more vCPUs than the host has logical CPUs. ESXi refuses the setting. So on ESXi an N-vCPU VM always has N real CPUs it can run on at once. The host as a whole may be overcommitted, and then worlds are time-sliced.
- Sibling vCPUs are kept roughly in step (relaxed co-scheduling: a vCPU that runs too far ahead of its slowest sibling is stopped until the sibling catches up).
- Default CPU shares are per vCPU, so a 4-vCPU VM is entitled to four times a 1-vCPU VM under contention.
- A vCPU-count change is a reconfigure task. vCenter records a `VmReconfiguredEvent` with the user, the time and (since 6.5) the old and new value.

What that means here:

- B7 is the guest-facing half of that model and is built the same way: one VMCS per vCPU (a world), the scheduler unit is the vCPU, an idle vCPU yields, turns are per vCPU (D11). None of it is thrown away by B21.
- B7 alone is below the benchmark: N vCPUs on one core is a setting ESXi does not allow. The catalog, this ADR and the Guests page say "N CPUs visible, one core of capacity". B21 is what reaches the benchmark, so it is Shipment 1 and comes next, not wave 11.
- B7 and B21 stay two iron threads. One flash that changes both the guest's CPU count and the host's cannot be diagnosed when it hangs.
- The vCPU-count save is an audit event (D10). Old and new value, as vCenter records them.

**Deviation.** ESXi does not allow more vCPUs than host logical CPUs; B7 does, on one core, until B21.

## Decision

| # | Decision |
|---|---|
| D1 | `MAX_VCPUS = 4`. A schedulable unit is (slot, vcpu). `unit = slot * MAX_VCPUS + vcpu`. |
| D2 | **N=1 identity rule.** With `vcpus == 1` every code path, every COM2 line and every table byte is what `main` produces today. Each new branch is behind `slot::vcpus() > 1` or `slot::current_vcpu() != 0`. |
| D3 | State is per guest by default. A second index (vCPU) is added only where a vCPU has its own CPU, LAPIC or exit-path CPU state. New banks `PerVcpu<T>` / `PerVcpuCell<T>` keep the `.p()` and `Deref` shape, so converting a static is a type-only edit. |
| D4 | One VMCS per vCPU. All vCPUs of a slot share the slot's EPTP, I/O bitmaps, MSR bitmap and the one shared host stack. No VPID, no APICv. |
| D5 | APs never run RayNu-F. vCPU 0 boots as today. An AP exists only after Linux sends INIT then SIPI. It starts in real mode at `CS = page << 8`, `CS.base = page << 12`, `RIP = 0`. |
| D6 | The LAPIC records INIT / SIPI / IPI. The exit path drains INIT and SIPI at the resume tail. A device module never touches a VMCS. |
| D7 | xAPIC only. x2APIC stays hidden. APIC ID of vCPU v is v. CPUID leaves 0xB / 0x1F stay zero (Linux and Windows fall back to leaves 1 and 4). |
| D8 | Platform timers (HPET sink, PIT raise, nominal tick) are driven by vCPU 0 exits only. Each vCPU has its own LAPIC timer. |
| D9 | 8259 / ExtINT goes to vCPU 0 only. |
| D10 | No Proven Core file is edited except `audit/integrity.rs`, which gains exactly one event variant, `GuestCpuSaved { spare_off, prev, n }`, tag 82. Calling public functions of the Proven Core is fine. |
| D11 | Scheduling is round-robin over units. A 4-vCPU guest gets four turns to a 1-vCPU guest's one. That is ESXi's default too (shares are per vCPU). |
| D12 | **One seam for touching another vCPU.** Only `lapic_virt::post_remote` writes another vCPU's LAPIC bank, and only `slot::wake_vcpu` kicks it. On one host core both are plain stores. B21 turns them into an atomic store and a host IPI without finding call sites. A source gate enforces it. |
| D13 | **The vCPU cap is a page fact, not a constant in the page.** `GET /perc/guests` reports `cpu_max`; the page builds its choices from it. B7 reports 4. B21 will report `min(4, host cores online)`, which is ESXi's rule. Until then the page says the vCPUs share one host core. |

## Rationale

- The guest-facing model matches ESXi's world: one VMCS per vCPU, the scheduler's unit is the vCPU, an idle vCPU yields. B21 adds host cores onto those seams and does not rewrite them.
- N=1 must stay byte-identical to the lived B6 path. Every new branch is gated so a one-CPU guest cannot observe B7.
- A device never writes a VMCS. INIT and SIPI are latched in the LAPIC and drained on the exit path, which is the only place a VMCS is current.
- APs start from architected INIT/SIPI state (ADR-016). They do not run RayNu-F and they do not have firmware state poked.
- Windows uses the same MADT, the same INIT/SIPI sequence and the same xAPIC, so the path stays open. Windows guests are B13 and are not tested here.
- One host core cannot give a 4-vCPU guest more than one core of capacity. Saying otherwise on the page or in the catalog would claim the ESXi rule B7 does not meet. B21 is the row that meets it, and it is Shipment 1 so the wave 9 soak runs on real cores.
- The vCPU-count save records the old value and the new one, as vCenter's `VmReconfiguredEvent` does.

## Consequences

- **No added throughput.** N CPUs are visible. They share one core of capacity. A 4-vCPU guest gets four scheduler turns to a 1-vCPU guest's one (D11).
- **N=1 is the lived machine.** COM2, ACPI and the exit path match `main` when the count is 1.
- **Outside the Proven Core** except `GuestCpuSaved`. Maturity levels are unchanged.
- **Known cost, not tuned.** On one core a vCPU that spins waiting for a descheduled sibling burns the rest of its 2 ms quantum. B21 removes the cause. Co-stop of a vCPU that runs ahead of its siblings is bounded by one quantum per sibling on one core and becomes real work in B21.
- **Not in this ADR's build:** host AP bring-up, x2APIC, APICv, VPID, posted interrupts, TSC-deadline mode, CPU hot-add (B19), pinning and NUMA (B17), shares and limits (B18), more than 4 vCPUs, SMBIOS Type 4 core counts.
- B7 is not lived until an Ubuntu product guest on the R640 reports more than one CPU over SSH. Nested QEMU and CI do not close the row.
- Scores stay put. HDA overall stays 99%.

## What B21 changes

B21 is the host half of the VMware model: every host core is brought up, enters VMX root and runs vCPUs. It gets its own plan. B7 leaves these seams so that B21 adds to B7 and does not rewrite it. The right-hand column is the starting point for that plan.

| B7 leaves | B21 does with it |
|---|---|
| `slot::current()` / `slot::current_vcpu()` are one word each (one CPU runs guests) | Per host core. Every `PerGuest` / `PerVcpu` bank follows without an edit. |
| `lapic_virt::post_remote` and `slot::wake_vcpu` are the only way to reach another vCPU (D12) | Atomic store, then a host IPI to the core that runs the target, which forces a VM exit. |
| A vCPU's `PerVcpuCell` bank is touched only while that vCPU is current, or through `post_remote` | That becomes the ownership rule: the core running the vCPU owns its bank. |
| Per-guest device state (virtio, IOAPIC, PIC, HPET, UART) is `PerGuestCell` with no lock | One lock per guest slot around device emulation. |
| `HOST_RSP_SHARED`: one host stack | One host stack, GDT, TSS and VMXON region per host core. |
| The scheduler picks the next unit for the one core | A ready queue per core; a halted world gives its core away; co-stop bounds sibling skew. |
| `guest_cpu::cpu_max()` returns `MAX_VCPUS` (D13) | Returns `min(MAX_VCPUS, host cores online)`; a larger saved count is refused at Start, as ESXi does. |
| Platform timers are driven by vCPU 0's exits (D8) | Driven by one host timer, not by any vCPU's exits. |
| EPT is shared by a slot's vCPUs with no flush (no VPID, one core) | An EPT change needs an INVEPT on every core running that slot. |
