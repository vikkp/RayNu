# ADR-016: RayNu-F — be the guest firmware for E5

- **Status:** Accepted
- **Date:** 2026-09-04
- **Pillars:** [Z] single binary · [A] audit ([V] architecture preserved — no Proven Core expansion)
- **Parent:** [ADR-009](ADR-009.md) (Mount Everest E5) · [ADR-014](ADR-014.md) (typed ISO / UEFI+virtio product boot) · supersedes the OVMF-relaunch **mechanism** used through Stage 46
- **Does not change:** E4 SHELL VMCS/EPT, `iso=0` path, Proven Core boundary (ADR-002), size budget (ADR-003)

## Context

Everest E5 needs a typed ISO to boot a UEFI installer to virtio-blk on real
R640 iron (`RAYNU-V-M7-ISO-INSTALL-OK`). The Stage 46 mechanism was: retain
the platform `OVMF.fd`, build a private VMCS + alias EPT, `VMLAUNCH` it at the
reset vector, and hand-emulate a whole PC (fw_cfg, ACPI/MTRR/GCD, PCI,
IDE/ATAPI, virtio, xAPIC/IOAPIC/PIC/PIT/HPET, 8042) until OVMF boots the ISO.

That mechanism reached, on iron: VMLAUNCH, past-SEC, DXE, CDROM-OK, VIRTIO-OK,
BOTH-OK, ATAPI-OK (`bf696ca`) and El Torito ELTORITO-OK (`0be7283`). But the
full product ISO (Stage 46) stalls **before** ATA (`ataio=0`): DxeCore parks in
`CoreWaitForEvent` on a timer event that never signals.

The ladder from `2d4ab51` → `4e16b59` (retaddr → ConIn → callsite → WFE
force-return → ZeroMem → preempt-skip → state4-poke → event-#PF inject) shared
one root defect: **we mutated OVMF's own internal control state to force
progress.** `CoreWaitForEvent(N, Events, OUT *Index)` must write `*Index`; the
force-return (`e0d5c55`) unwound the frame without it. Downstream, BDS then
walked a NULL `EFI_EVENT` (`r14=0` → `cmp [r14-0x48],'evnt'`) and page-faulted
(`#PF cr2=0xffffffffffffffb8`). The next five pins chased that fault we
created; `4e16b59` injected the `#PF`, OVMF's own handler ran, dumped a real
`#PF`, and `CpuDeadLoop`ed. Each pin cost a physical Cruzer flash. Nested QEMU
reaches ATAPI-OK where iron does not — the divergence is timer/interrupt
delivery behind our xAPIC/IOAPIC trap, not the boot logic.

Two lessons:

1. **Reaching into another firmware's private state to force it forward is a
   self-inflicted-wound generator.** We do not own OVMF's invariants; forcing
   one (a return without its OUT param) violates the next twenty.
2. We are reimplementing a device model by trial-and-error, one physical boot
   per bit of information, to satisfy a third-party firmware whose contract we
   only partially meet.

## Decision

1. **RayNu-F: be the guest firmware ourselves.** For the E5 product path, RayNu
   presents a **minimal, correct UEFI boot environment** to the ISO's own
   bootloader (`\EFI\BOOT\BOOTX64.EFI` — GRUB / systemd-boot / the Linux EFI
   stub) instead of relaunching and puppeting OVMF. We own the contract:
   an `EFI_SYSTEM_TABLE` + boot services with `BlockIo` / `SimpleFileSystem`
   over the CD (El Torito, already reached on iron) and virtio-blk, `LoadImage`
   / `StartImage`, serial `ConIn`/`ConOut`, `GetMemoryMap`/`ExitBootServices`,
   and a timer tick we deliver on our own schedule. Because we author every
   structure, **there is no third-party firmware internal state to corrupt.**

2. **RayNu-F is a subsystem, not a second binary.** It compiles into the single
   `r640-hypervisor.efi` ([Z] preserved). It runs inside the guest VMCS/EPT we
   already build. Naming: RayNu-**V** = the hypervisor; RayNu-**F** = the guest
   boot firmware it presents to a typed ISO.

3. **RayNu-F is OUTSIDE the Proven Core** (ADR-002). It is guest firmware, like
   the Linux boot protocol and device emulation. No LOC-budget change, no new
   Verus obligation. Standard Rust + tests (two-file convention).

4. **No third-party firmware state mutation (governance).** Neither RayNu-F nor
   the residual OVMF path may force or rewrite another firmware's internal
   control state (stack frames, event/object structures, gState, forced
   returns, injected faults to steer control flow) to manufacture progress.
   Drive guests only through **architected inputs**: interrupts, device
   register/DMA responses, memory the spec says is ours, and documented ABI
   returns. See the honesty constraint added to `CLAUDE.md`.

5. **Disable the Stage 46 forcing.** The `3k–3o` mutations
   (`guest_uefi_waitforevent_force_return` / `apply_waitforevent_return`,
   `try_firmware_wfe_state4_poke`, `deliver_firmware_wfe_event_pf`) are gated
   off (`RAYNU_F_NO_FW_STATE_MUTATION`). The retained-OVMF VMLAUNCH stays as a
   diagnostic/fallback, but it no longer mutates firmware internals. Refuse
   `4e16b59` / `--run 33820727776` (event-#PF inject → real `#PF` + CpuDeadLoop).

6. **Do not claim `RAYNU-V-M7-ISO-INSTALL-OK`. HDA `last_commit` stays
   `2b795a0`.** RayNu-F lands as honest scaffolding first (no EFI system table,
   no boot services, no ISO boot); each capability closes on its own evidence.

7. **ADR-014 typed-ISO contract stands.** RayNu-F *is* the "UEFI guest firmware"
   the ADR-014 product path assumed; `linux_iso` / `windows_iso` /
   `generic_uefi` and the boot-order spec are unchanged. `windows_iso` stays in
   the model.

## Consequences

- Iron flash discipline changes: the fast iteration harness is **nested / QEMU**
  (which already reaches ATAPI-OK); iron flashes are reserved for confirming the
  genuinely iron-specific parts (MTRR/GCD/phys-width, real-silicon LAPIC/timer
  delivery). Stop spending one physical boot per micro-experiment.
- RayNu-F must still deliver a periodic timer tick to the guest bootloader/kernel;
  the interrupt-delivery understanding the OVMF path lacked is now **our own**
  timer arch responsibility, not a puppeting hack.
- The retained-OVMF relaunch path stays compiled (past-SEC/DXE/ATAPI/El Torito
  evidence is real) but is a diagnostic/fallback, not the E5 close mechanism.
- Proven Core, ADR-002, ADR-003 size budget unchanged. RayNu-F guest firmware
  follows ADR-003 (lazy/zstd; 20 MB hard limit) if it grows embedded assets.
- Audit events for RayNu-F boot-service milestones live in the management/guest
  plane ([A]).

## RayNu-F stages (lived, tick only on evidence)

| # | Name | Track | Close when |
|---|------|-------|------------|
| **F0** | Scaffold | host | **CLOSED** — `RAYNU-V-RAYNU-F-SCAFFOLD-OK`: subsystem declared, outside Proven Core, honesty invariants (not functional / not ISO / never puppets foreign firmware). |
| **F1** | System table + serial console | host | **CLOSED (host)** — `RAYNU-V-RAYNU-F-TABLES-OK`: byte-exact UEFI 2.10 x64 `EFI_SYSTEM_TABLE` (120 B) + `EFI_BOOT_SERVICES` (44 fn) + `EFI_RUNTIME_SERVICES` (14 fn) + `SIMPLE_TEXT_OUTPUT/INPUT`, valid header CRC32s, `L"RayNu-F"` vendor; every fn pointer is a 14-byte guest trampoline (`mov r10,rdx; mov eax,id; mov dx,0x5246; out dx,eax; ret`) so a call is an ordinary I/O exit (no VMCALL, outside Proven Core); host dispatcher implements `ConOut.OutputString/Reset/TestString` + no-op cursor/attribute, `ConIn.ReadKeyStroke` → `EFI_NOT_READY`, boot/runtime → `EFI_UNSUPPORTED` (honest). Wired into `emulate_io_port`. **No guest has executed these tables yet.** |
| **F2** | PE32+ loader + guest launch | host + QEMU | Load a PE32+ EFI application into the guest, map our tables, enter it long-mode with `(ImageHandle, *SystemTable)`; a RayNu-F-owned test app calls `ConOut->OutputString` → serial prints `RAYNU-V-RAYNU-F-CONOUT-OK`. That marker is produced **only** by a live guest VM-exit, never by host/CI unit tests. |
| **F3** | Memory services + owned timer tick | QEMU | `AllocatePages/Pool`, `GetMemoryMap`, `ExitBootServices`; a periodic tick we deliver (our arch-timer). |
| **F4** | BlockIo over CD + virtio-blk | QEMU → iron | `EFI_BLOCK_IO_PROTOCOL` on the El Torito CD (already reached on iron) and the virtio-blk install target. |
| **F5** | SimpleFileSystem + LoadImage/StartImage of the ISO's `\EFI\BOOT\BOOTX64.EFI` | QEMU → iron | GRUB / Linux EFI stub runs under RayNu-F. |
| **F6** | Installer to disk | iron | `RAYNU-V-M7-ISO-INSTALL-OK` — the only E5 close. |

Fast harness is nested/QEMU; iron flashes only for iron-specific confirmation
(MTRR/GCD/phys-width, real-silicon LAPIC/timer). No stage closes on host/CI
prints alone past F1.

## Anti-self-wound rule (why this won't recur)

The governance constraint (#4) is the durable fix. A change is a **self-inflicted
wound** when it makes forward progress by editing a component's private state
that we do not own the invariants for. The tell in the record: a fix that
"forces X to return / advances RIP past a check / pokes a gState / injects a
fault to steer flow" — each of those in `3k–3o` created the next hang. RayNu-F
removes the category: we own every structure, so there is nothing foreign to
corrupt, and every wait completes because *we* signal it.
