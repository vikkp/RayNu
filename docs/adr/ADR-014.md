# ADR-014: Multi-guest-OS image and install path

- **Status:** Accepted
- **Date:** 2026-08-21
- **Pillars:** [Z] [A] ([V] architecture preserved — no Proven Core expansion)
- **Does not block:** E4 SPA VMLAUNCH (P0-14). Shadow VMCS / re-entry stays current priority.

## Context

G0 today boots a packed Linux bzImage (`guest/linux_boot.rs`, M3). M7.3/M7.7 ISO
work is a **documented kernel-extract** MVP: register an ISO metadata row, then
bind the existing bzImage/initrd staging path and a virtio-blk install disk.
El Torito / CD-ROM attach is GuestVisible (Stage 40). Firmware ATAPI
`READ(10)` is closed on iron (Stage 44). E5 product close is still a
distro installer, not LBA stamps.

That is honest for lab/M4 and for the stamp contract. It is **not** the product
install model. If SPA “ISO install” stays hard-wired to Linux boot protocol
(cmdline, initrd, `load_bzimage_guest`), we paint the product into a Linux-only
corner. Windows (and other UEFI guests) would then need a second, incompatible
install stack.

virtio-blk and virtio-net already work as the default backend for Linux **and**
Windows guests (Windows needs virtio drivers in the guest — later). The missing
piece is the **image type + firmware + boot order** contract, not a new disk
emulator.

## Decision

1. **Treat “guest image” as a type, not “always a Linux kernel.”** Management-plane
   types (outside Proven Core):

   | Type | Wire tag | Role |
   |------|----------|------|
   | Linux ISO | `linux_iso` | Distro installer media (UEFI + virtio) |
   | Windows ISO | `windows_iso` | Windows installer media (later; same firmware path) |
   | Generic UEFI | `generic_uefi` | Any El Torito / EFI boot image |
   | Linux bzImage | `linux_bzimage` | **Lab/M3–M4 G0 only** — packed Linux boot protocol |

2. **Product boot path is UEFI guest firmware + virtio disk first** (El Torito /
   OVMF-style): attach ISO as CD, empty virtio-blk as install target, boot order
   CD then disk. “Load bzImage and jump” is **not** the product installer. It
   remains the G0 lab path.

3. **SPA create/start must grow a boot spec**, not assume Linux cmdline/initrd:

   - firmware (`uefi` | `linux_boot_protocol`)
   - disks (virtio-blk sizes / images)
   - ISO attachment (id + type)
   - boot order (CD, disk, …)

   Today’s `POST /vms/{id}/spec/{cpu}/{ram}/{disk}/{iso}` stays valid for E4
   SHELL start. The extra fields land when the real ISO installer is built —
   they must not default to bzImage jump.

4. **Linux-specific boot stays in `guest/linux_boot.rs`.** Do not promote it into
   the Proven Core (ADR-002 already lists “Linux boot protocol” as outside). Do
   not make `vmx/` or `memory/` parse `HdrS` / initrd. A future `guest/` loader
   facade may dispatch on `GuestImageType`; the Linux module remains one backend.

5. **Windows is in scope later, not this E4 slice.** We are not shipping Windows
   install now. The type table and UEFI-first boot path exist so ISO work starts
   multi-OS clean. virtio drivers in the Windows guest, Secure Boot, and WHQL
   are residual — not E4, not a reason to keep bzImage-only install.

6. **Everest E5** may still close on a **Linux** distro ISO once the UEFI+virtio
   installer path works. That close does **not** license deleting `windows_iso`
   / `generic_uefi` from the model.

## Consequences

- Current E4: G0 Linux bzImage (lab) + SPA SHELL VMLAUNCH (scheduler proof).
  Unchanged.
- M7.3 extract-boot remains the documented **MVP residual**, labelled lab, not
  the product default.
- Next ISO work implements El Torito / guest UEFI firmware attach before any
  new “extract and jump” shortcuts.
- Proven Core LOC budget unchanged. Guest firmware blobs (OVMF-style) follow
  ADR-003 (lazy/zstd; 20 MB hard limit).
- Audit events for image register / attach / boot-firmware selection stay in
  the management plane ([A]).

## Stage 0 (host) — boot spec on the wire

Closed as a **host** gate (`RAYNU-V-M7-E5-BOOT-SPEC-OK`). Not iron. Not Everest E5.

- `POST /vms/{id}/spec/{cpu}/{ram}/{disk}/{iso}` stays valid. `iso=0` is E4 SHELL
  (`image_type = None`). `iso != 0` without a type defaults to `linux_iso`.
- Optional fifth segment: `/{linux_iso|windows_iso|generic_uefi}`.
  `linux_bzimage` is rejected (409). Type without ISO is rejected.
- REST/SPA JSON carries `image_type`, `firmware`, `boot_order`.
- El Torito **catalog parse** is host-only (`mgmt/el_torito.rs`). Parse is not
  attach. `attach_cdrom_uefi` stays `UnsupportedOnFirmware`.
- `vmx/launch.rs` E4 SHELL VMLAUNCH is unchanged. No guest UEFI firmware blob
  (ADR-003 size). Do not claim `ISO-INSTALL-OK` from this slice.

## Stage 1 (host) — host CD-ROM attach

Closed as a **host** gate (`RAYNU-V-M7-E5-CDROM-ATTACH-OK`). Not iron. Not Everest E5.

- [`attach_cdrom_host`](../../mgmt/iso.rs) parses El Torito and records a
  `CdromAttach` (`Detached` | `Parsed` | `AttachedHost`). Product types require
  an EFI catalog. Lab `linux_bzimage` is rejected.
- REST: `POST /iso/{id}/attach[/{linux_iso|windows_iso|generic_uefi}]` → 201
  when the host CD-ROM model is armed. `GET /iso/attach` returns attached count.
  Until ISO blob upload exists, REST parse uses the host mock EFI prefix.
  That is host attach, not the operator's distro ISO.
- `attach_cdrom_uefi` stays `UnsupportedOnFirmware` (M7.3 honesty).
- SPA **Attach CD** is host attach. Not guest UEFI. Not VMLAUNCH.
- `vmx/launch.rs` E4 SHELL (`iso=0`) is unchanged. No OVMF blob (ADR-003).
- Do not claim `ISO-INSTALL-OK` or Mount Everest from this slice.

## Presence rule (closes the Stage appendix)

The ADR-014 **Decision** (typed guest image + UEFI-first boot) stands.
Stages 0–35 remain closed host gates. Stages 25–35 (`present` / `admit` /
`read` / `copy` / `place` / `apply` / `commit` / `latch` / `seal` /
`lock` / `hold`) were bookkeeping only. **There are no further *Absent
bookkeeping stages.** The Stage appendix is not a license for infinite
gates. No new SPA button that only advances a host flag.

Closed as a **host + QEMU** gate (`RAYNU-V-M7-E5-LIVE-BYTES-PRESENT-OK`).
Not iron. Not Everest E5.

- Pre-EBS, [`probe_ovmf_esp`](../../boot/ovmf_esp.rs) reads
  `\\EFI\\RayNu\\OVMF.fd` into a static retained buffer (ADR-003
  split-mode). That is **not** a PE embed and is **not** a 4 MiB BSS
  ship of OVMF in the `.efi` file.
- [`guest_uefi_live_esp_bytes_present`](../../vmx/launch.rs) is true
  only when [`accept_real_ovmf_bytes`](../../boot/ovmf_esp.rs) accepts
  the retained image:
  - `1 MiB <= len <= 4 MiB` (ADR-003 cap)
  - `_FVH` at offset `0x28`
  - at least 64 KiB of nonzero bytes (rejects the 80-byte mock, 4 KiB
    floor, and zero-padded 1/2/4 MiB fixtures)
- Host `cargo test` does not load ESP bytes, so presence stays false
  unless a unit test calls `retain_ovmf_bytes` with an accepted image.
- QEMU proof: `tools/run-qemu.sh` copies a system `OVMF.fd` /
  `OVMF_CODE*.fd` (1–4 MiB) onto the ESP. Iron Cruzer flash
  (`tools/flash-cruzer-esp.sh`) does the same onto `EFI/RayNu/OVMF.fd`.
  `qemu-boot-test.sh` requires
  `RAYNU-V-M7-E5-LIVE-BYTES-PRESENT-OK` on serial.
- Presence is **not** a private guest-UEFI VMCS by itself. Stage 37
  allocates a **private guest-UEFI VMCS** + alias EPT and issues
  `VMLAUNCH` of the **retained** bytes at `0xFFFF_FFF0` (unrestricted
  guest, real mode). That path is **not** the E4 SHELL VMCS/EPT.
- QEMU (VMX) proof: `RAYNU-V-M7-E5-LIVE-BYTES-PRESENT-OK` then
  `RAYNU-V-M7-E5-OVMF-VMLAUNCH-OK` after a real entry (first VMEXIT
  that is not a VM-entry failure / reset-vector fetch miss). Host
  `cargo test` still does not execute the instruction
  (`PrivateVmcsNotLaunched`).
- Stage 37 first exit was triple-fault (`reason=0x2`) at
  `RIP=0xFFFF_FEB4`. OVMF SEC 4M CODE does `mov eax, 0x640; mov cr4,eax`,
  which clears `CR4.VMXE`. Under VMX that write is `#GP(0)` into an
  empty IDT (same class as Linux `startup_64`; E4 already host-owns
  VMXE). Stage 38 host-owns `CR4.VMXE` (mask + read-shadow), maps 32 MiB
  low identity RAM, and VMRESUMEs a short I/O/CPUID/MSR loop.
  `RAYNU-V-M7-E5-OVMF-ALIVE-OK` means at least two non-triple-fault
  exits or a guest HLT — not full SEC/PEI/DXE and not an installer.
- Stage 39 forwards COM1/COM2 (16550 THR, DLAB-aware) to host serial
  and keeps the private VMCS up to 256 exits. `RAYNU-V-M7-E5-OVMF-PAST-SEC-OK`
  means linear RIP left the last 64 KiB (`0xFFFF_0000`) **and** PEI-style
  PCI config I/O (`0xCF8`/`0xCFC`), a firmware COM byte, or a guest HLT.
  That is past SEC, not full PEI/DXE, not virtio-in-guest, not installer.
- Stage 40 wires [`attach_cdrom_uefi`](../../mgmt/iso.rs) for real.
  After `FirmwareArmed`, the record becomes `GuestVisible` and media is
  presented on a PIIX3-class PCI IDE/ATAPI function (`00:00.0`) with
  primary PIO (`0x1F0`/`0x3F6`) on the **private** guest-UEFI VMCS.
  Unarmed `attach_cdrom_uefi` still returns `UnsupportedOnFirmware`.
  `RAYNU-V-M7-E5-OVMF-CDROM-OK` means past-SEC **and** the guest
  enumerated that IDE function or read an ATAPI sector. That is CD
  visible to this guest — not full DXE, not virtio-in-guest, not
  installer.
- Stage 40 stopped on EPT at `0xFCF8_F000` because unhandled CMOS `IN`
  returned `0xFF` (PEI invented nearly 4 GiB of RAM). Stage 41 serves
  honest CMOS memory size, QEMU fw_cfg `RAM_SIZE`, an i440FX host
  bridge at `00:08.0` (PEI only probes `00:00.0` Device ID; that slot is
  the guest IDE), PIIX3 ISA at `00:01.0`, and EPT sink-resume for
  high MMIO so PEI can continue. PCI config data uses QEMU's
  `CF8 | (CFC & 3)` byte offset so an `inb(0xCFC)` after CF8=`0x0E`
  returns Header Type `0x80`, not Cache Line Size `0`. After DXE evidence the private VMCS
  keeps a short resume tail then fail-softs to E4 (does not burn the
  remaining 2048 I/O exits). Closed on nested VT-x (raynuvsrv1):
