# ADR-011: Evidence / Verbose Mode Triggered by ESP Flag File

- **Status:** Accepted
- **Date:** 2026-07-24
- **Pillars:** [V] [A] [Z] [D]

## Context

ADR-010 established the living verification paper as a progressive public
audit artifact. Evidence blocks must come from real runs (serial logs,
audit-ring events, gate checklists, Verus/Kani transcripts). Manually
reconstructing those artifacts after every R640 / iDRAC boot is friction
and risks incomplete or retrospective recording.

We already have Tier-1 serial / iDRAC virtual console and an audit ring
inside the Proven Core. A simple, reversible way for the single `.efi`
binary to emit structured evidence on demand is required so that updating
the living paper becomes a download-and-paste step.

## Decision

1. The shipping binary remains a single `r640-hypervisor.efi` (ADR-003).
   No separate "verbose" build is required for normal use.

2. Evidence / verbose mode is activated at early boot by the **presence**
   of a flag file named `paperverbose.txt` on the EFI System Partition
   (or the volume from which the `.efi` was loaded). A conventional
   location such as `/EFI/RayNu/paperverbose.txt` is also recognised.
   The file may be empty; presence alone is the signal. Matching is
   case-insensitive to accommodate FAT semantics.

3. When the flag is detected the hypervisor:
   - Raises audit-ring verbosity for the duration of the boot / run.
   - Executes a small, deterministic set of self-tests / gate checks
     appropriate to the current milestone maturity.
   - Emits a structured Evidence Bundle (serial + optional small dump
     on the ESP / virtual media) that already follows the evidence-block
     format defined in the living paper (date, build identity / commit
     or content hash, maturity claims that never exceed actual code
     maturity, artifact references, one-line observations).
   - Records an audit event that evidence mode was activated and from
     which volume.

4. Evidence mode **never** claims L2 or L3. Formal Verus / Kani
   transcripts remain offline host-side artifacts (ADR-001, ADR-008).
   The EFI can only ever report runtime-enforced (L1) behaviour plus
   self-test results.

5. The default path (flag file absent) is unchanged: minimal logging,
   fast boot, production-oriented behaviour. Size and boot-time impact
   of the detection path must be negligible.

6. Detection logic and any new self-test code that touches Proven Core
   modules (VMX, EPT, allocator, etc.) must follow the existing
   maturity model (ADR-006) and four-file convention. No expansion of
   the Proven Core boundary (ADR-002) is authorised by this ADR.

## Consequences

### Positive
- Cookie-cutter evidence generation on real R640 / iDRAC virtual media.
- Living paper updates become download + paste of system-generated logs.
- Single binary and zero permanent configuration preserved.
- Fully reversible: delete the flag file and the next boot is normal.
- Strengthens the audit trail ([A]) and the honesty of the living paper ([V]).

### Negative / Risks
- Early-boot FAT / volume enumeration must stay minimal and robust.
- Extra audit traffic in evidence mode must not overwhelm the ring or
  change production behaviour when the flag is absent.
- Operators must understand that L2/L3 claims still require offline
  Verus/Kani artifacts.

### Neutral
- PXE / network boot has no local FAT by default; evidence mode over
  pure network boot is out of scope for the initial implementation
  (USB / iDRAC virtual media is the primary path).
- Future extensions (EFI variable trigger, optional run-ID inside the
  flag file) require a follow-up ADR or a small amendment if they change
  the contract.

## Implementation Notes

- Detection occurs after basic UEFI services and simple FAT access are
  available, before or immediately after the primary "RayNu-V alive"
  path.
- Preferred flag locations (checked in order):
  1. `/paperverbose.txt` (volume root)
  2. `/EFI/RayNu/paperverbose.txt`
- Build identity (git commit hash or binary content hash) is included
  in every Evidence Bundle so the living paper can cite the exact
  revision.
- First implementation target: M0 / M1 gate support. Later milestones
  add richer self-tests under the same flag.
