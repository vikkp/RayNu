# ADR-018: Post-Everest M8 — operator product hardening

- **Status:** Accepted
- **Date:** 2026-09-11
- **Pillars:** [Z] single binary · [A] audit · [D] iDRAC-native ([V] architecture preserved — no Proven Core expansion)
- **Parent:** [ADR-009](ADR-009.md) (Mount Everest / M7) · [ADR-014](ADR-014.md) (typed ISO) · [ADR-016](ADR-016.md) (RayNu-F) · [ADR-017](ADR-017.md) (F7 reboot-to-disk)
- **Does not change:** Proven Core boundary (ADR-002), size budget (ADR-003), iron-only `RAYNU-V-M7-ISO-INSTALL-OK`

## Context

Mount Everest (ADR-009 M7) is the shippable **single-host** operator product loop:

> Ship the EFI → boot on a **real PowerEdge R640** → **network-reachable** vSphere-like UI → **deploy a Linux ISO**.

That loop **closed on iron** 2026-09-11. EFI `f72b4276` / CI `--run 34552377351` (no `--raynu-f`, UDisk front USB 2): SKIP-OVMF-OK → E4-CONTINUE-OK → coexist `HOST-NIC-HTTP-OK` on `10.99.99.145:8443` → SPA Start of RayNu-F product ISO → Alpine `setup-disk` → **`RAYNU-V-M7-ISO-INSTALL-OK`** on COM2 → F7 → **`RAYNU-V-RAYNU-F-DISK-BOOT-OK`** → second Linux `root=UUID=814a97a0-d3be-4a64-8611-b3dbd9859201` → `login:`. Evidence: [`docs/evidence/r640/2026-09-11-f72b4276-phase-b-spa-iso-install-disk-boot-ok.md`](../evidence/r640/2026-09-11-f72b4276-phase-b-spa-iso-install-disk-boot-ok.md).

What remains is **operator polish**, not the Everest loop:

| Gap | Needed for Everest? | Why it is still real work |
|-----|---------------------|---------------------------|
| Leftover-DRAM install disk persist across a **host** reboot of RayNu-V | No (E5 is guest reboot) | Operator loses the guest disk if the hypervisor reboots |
| TLS on `:8443` (plaintext HTTP closed Everest; ADR-009 deferred TLS) | No | Bring-up LAN is not a production mgmt plane |
| Auth beyond the bring-up token | Soft | `raynu-v-bringup` is a lab latch |
| Guest console UI (VNC / web; serial worked) | No | Operators should not need iDRAC SOL to type in the guest |
| ISO blob upload via SPA (ESP ISO counted) | Soft | Catalog-from-ESP is the Everest path |
| UEFI catalog persist (`UnsupportedOnFirmware`) | No | Host `std::fs` catalog closed M7.2 |
| Multi-distro / Windows install (ADR-014) | No | Alpine 3.21 on virtio is the E5 close |

ADR-009 named **M8 = cluster** (vMotion-like, DRS-like, hot-add). That sketch must not jump the queue: a single-host that forgets disks on HV reboot and serves plaintext HTTP is not ready for live migrate. Treating the polish table as “Everest still open” is dishonest now that COM2 printed the markers.

## Decision

1. **Record M7 Mount Everest CLOSED on iron.** Pin `f72b4276` / `34552377351`. **Rollback kit:** GitHub Latest [`v0.1.0-everest-closed`](https://github.com/vikkp/RayNu/releases/tag/v0.1.0-everest-closed) (EFI SHA256 `e74460ff0e248a06d2e4ab546684d1006edd25855f50c8dc27dc202facab9cbc`). Host/CI still never print `RAYNU-V-M7-ISO-INSTALL-OK`. Latitude/QEMU still ≠ R640. Do not bump HDA overall to 100%.

2. **M8 is operator product hardening** — the polish table, built **step by step** in this order (do not skip ahead without an explicit plan rewrite). **M8.7** is that rewrite for Bar B: it may proceed while M8.4–M8.6 stay open.
   - **M8.0** Persist the leftover-DRAM install disk across a **host** reboot of RayNu-V (NVMe/ESP-backed virtio, not “hope DRAM is still there”).
   - **M8.1** TLS on the coexist listen (`:8443` or 443); plaintext remains a lab fallback.
   - **M8.2** Real auth beyond the bring-up token (operator credential, not `raynu-v-bringup` as the product default).
   - **M8.3** Guest console UI (web/VNC or equivalent) so serial SOL is not the only keyboard.
   - **M8.4** ISO blob upload via SPA/REST (ESP-staged ISO stays valid).
   - **M8.5** UEFI catalog persist (replace `UnsupportedOnFirmware` with a real SFS/NVMe write).
   - **M8.6** Windows / multi-distro install later under ADR-014 — same UEFI+virtio model; not a parallel firmware rewrite.
   - **M8.7** PERC H740P mailbox on the empty spare VD (**RAYNU-SPARE**). Host slice packs MFI frames and refuses the Ubuntu-sized VD. The H740P Mini is Fusion/Ventura (`1000:0016`). Firmware state is `outbound_scratch_pad_0` (BAR + `0xB0`), not the xscale word `outbound_msg_0`. Iron `2dd2b412` read that xscale word as zero and did not reset. The mailbox is one 64-bit MFA store to inbound port `0xC0` after the status nibble is READY, then one IOC init and one LD list. Iron `22ce3728` showed READY (`0xb73c0fed`). This image does not store doorbell `0x00`. `skip PERC` stays until the spare is explicitly attached. M8.4–M8.6 remain open; Bar B does not wait on them. Iron marker `RAYNU-V-M8-PERC-LUN-OK` is never printed from host/CI. Outside Proven Core.

   **Amendment (2026-09-26):** the first fwstate EFI treated `outbound_msg_0` as the Harpoon status word. Linux `megasas_read_fw_status_reg_fusion` does not. A zero there does not authorize OCR. All-zero scratch pads (`mapped=0`) stop the milestone; they do not start an offset hunt. Iron `22ce3728` read scratch pad 0 as `0xb73c0fed`: state nibble READY, low 16 bits max commands 4077. Those low bits are not `MFI_RESET_REQUIRED`. The following image posts IOC init because the nibble is READY. It still does not store the doorbell, and it does not READ. Iron `83ae471e` confirmed READY (`allow=1`, same `0xb73c0fed`) and skipped the post: `perc ioc skip above4g`. The DMA buffer in that image was a BSS static, and scratch pad 1 bit 25 (64-bit DMA) was clear. The image after that takes eight pages from the post-EBS frame pool (that boot's pool started at `0x1000000`) and still does not store the doorbell. Iron `7577f934` lived that post: IOC status `0x00`, LD list `n=2` `pick=1` (id 0 UBUNTU0 `429496467456`, id 1 RAYNU-SPARE `3169417691136`). The doorbell was only loaded (`0x40000000`). The following image posts one READ(16) of LBA 0 and, only if that status is 0, one READ(16) of the last LBA, then offers the spare as read-only virtio at `00:04.0`. It reuses the completed DCMD page for the SCSI frame and the LD-list page for the 512-byte payload plus 32 bytes of sense. It does not write, and it does not store the doorbell. `RAYNU-V-M8-PERC-LUN-OK` stays unprinted until a guest read of that virtio device succeeds.

   **Amendment (2026-09-27):** that chain is one EFI. A non-zero status or a poll timeout stops the stage. There is no retry, no WRITE, no second target, and no H840. The install disk stays the Toshiba (`skip PERC`). Host and CI still never print the iron marker. Iron `985495bef9fa` lived both READs (`status=0x00`, LBA 0 signature 16 zero bytes, last LBA `6190268927`) and Linux enumerated `vdc` at `6190268928` sectors. The guest marker did not reach COM2 because it used `write_line`, which earlycon drops. The following image prints that marker with `write_line_nowait`. Iron `9c37fcae` lived that print: `boot: perc virtio rd lba=0 ok` and `RAYNU-V-M8-PERC-LUN-OK` during the `vdc` probe. A later `dd` of `/dev/vdc` copied 512 bytes whose first 16 were zero. The spare stays unpartitioned. A read is not a boot disk. The following image posts one WRITE(16) of the spare's last LBA, then reads that LBA back. The payload is 16 bytes `RAYNU-SPARE-WR16` and 496 zeros. LBA 0 is not written. Virtio stays read-only. `RAYNU-V-M8-PERC-WRITE-OK` prints only on iron, with `write_line_nowait`, after the readback matches. Host and CI never print it. There is no retry. Iron `f0a7aabb4131` lived that write: `boot: perc write status=0x00` at LBA `6190268927`, readback `status=0x00`, then `boot: perc write rd lba=6190268927 match` and `RAYNU-V-M8-PERC-WRITE-OK`. LBA 0 signature stayed 16 zeros. Virtio stayed read-only. Linux still booted the Toshiba. One sector is not a boot disk.

3. **Cluster / elasticity becomes M9.** vMotion-like live migrate, DRS-like placement, and hot-add stay out of M7 **and** out of M8. Ghost page-transfer proofs (M6.3 / ADR-004) remain substrate only.

4. **Outside Proven Core.** Persist, TLS, auth, console, upload, catalog, Windows install, and the M8.7 MegaRAID mailbox stay outside unless a future ADR expands the boundary (default **no**). Size still ADR-003.

5. **Living plan:** [`docs/m8_plan.md`](../m8_plan.md). HDA “next move” tracks M8.0 first. Public site Everest page records the close; it does not pretend TLS is done.

## Consequences

- ADR-009 decision 4 (“M8 = cluster”) is **superseded for the milestone number**. Cluster intent is unchanged; the number is M9. Cite this ADR, not a silent rewrite of 009’s history.
- Closing Everest does **not** close production polish. Overall HDA stays **99%** until M8 named gaps shrink with evidence.
- Do not print `ISO-INSTALL-OK` from host/CI to “prove” M8.0. Iron persist marker is `RAYNU-V-M8-DISK-PERSIST-OK` (minted in [`docs/m8_plan.md`](../m8_plan.md)). Host/CI print `RAYNU-V-M8-DISK-PERSIST-HOST-OK` for the file round-trip only.
- Do not start product vMotion on the M8 critical path.
- Iron Phase B reference remains `f72b4276` / `34552377351`. **M8.0 flash rollback** is GitHub Latest [`v0.1.0-everest-closed`](https://github.com/vikkp/RayNu/releases/tag/v0.1.0-everest-closed) (tag → that SHA; CI `--run 34552377351`; COM2 `build: sha=f72b4276d198`; EFI SHA256 `e74460ff0e248a06d2e4ab546684d1006edd25855f50c8dc27dc202facab9cbc`). Do not flash a later persist prototype as the known-good. Do not F11 `34548550755` / `7f8dc0a9` (`curl: (7)`), `34546680282` / `31f1ea0c` (G0 BAR hole), or earlier Phase B fails. `releases/v0.1.0-adr013-baseline` is the pre-native-NIC preserve, not this close.
